- **Origin:** the DST status review (2026-06-22) plus the world-class-opportunities deep research (2026-06-25), which independently reached the same verdict: of everything DST could grow into, **conformance is the single highest-leverage move** — the keystone that converts an excellent *simulator of the mock* into a *correctness guarantee about the running system*, and the gating prerequisite under a whole class of downstream guarantees. None of this requires touching the core engine.

**Framing.** DST today is genuinely world-class **for what it simulates**: a canonical virtual-time event loop, PCT/DPOR/Hypothesis exploration, Wing-Gong linearizability, declarative faults/latency, multi-node partitions, coverage-guided mutation, bit-exact replay, reachability assertions, and a replayable-bundle DX. This RFC does not rebuild any of that. It closes the one structural gap the engine sits behind: **its oracle horizon is the mock port.** Every invariant DST proves holds against [`forze_mock`](src/forze_mock/adapters/_mvcc.py), not against Postgres/Redis/Mongo. Until that gap is closed, every sentence of the form *"the simulator proves X under fault"* honestly reads *"X holds against a model we wrote"* — and a striking number of the framework's most valuable would-be guarantees (a propose-then-validate dry-run for agent writes; compiling domain invariants into oracles; an agent-authoring correctness verdict) silently collapse to *tautologies against a correct-by-construction mock* the moment you ask "…against what?". Conformance is what makes the answer "against the real engine."

**Why this matters for the AI-future direction.** Forze's intent is to be strong, safe glue for backend architecture and orchestration that lets AI-powered apps grow faster — not a LangGraph/Temporal clone. That bet rests entirely on *trust*: an agent authoring or operating a Forze app must be able to get back a verdict — "this change is correct," "this write would be accepted" — that means something. Today every such verdict runs on the mock. Conformance is the substrate that lets Forze honestly tell an agent *"this passed"* and have it refer to production. It is not the flashy part of the AI story; it is the part without which the rest is a green checkmark over an unverified model — the precise false-confidence failure mode that is most dangerous inside an automated loop.

## 1. Summary

The keystone, plus three supports — ordered by leverage, not by independence:

**A. Conformance — prove the mock behaves like the real adapter at the declared isolation level (THE keystone).** Build a differential battery on the shipped forced-interleaving driver: a catalog of classic isolation anomalies, each a deterministic two/three-transaction interleaving with a *known verdict per level*, run against **both** the mock and a **real backend via testcontainers**, asserting *mock ≡ real*. The verdict oracle and — far more importantly — the **allowed-divergence contract** (what counts as a real disagreement vs. a permitted implementation difference) **are the actual product** (§4.A.3–A.4). This retroactively gives every DST-derived claim its teeth and verifies the otherwise self-attested [`TxCapabilities.isolation`](src/forze/application/contracts/transaction/ports.py) ceiling against reality.

**Scope discipline, stated up front:** conformance is flagship-grade **only for the transactional-isolation family** (Postgres first; Mongo as snapshot-isolation). The general "mock ≡ real for every port" matrix (cache TTL, queue redelivery, dlock fencing, storage range reads, …) is an explicit **non-goal** (§3): it has no shared equivalence vocabulary, would require a new per-family allowed-divergence contract layer, and is the classic way differential suites die — drowned in false positives (engine null-ordering, JSON-shape quirks, abort-vs-block) until someone disables them. We ship the isolation differential deep and honest; we do not ship the matrix.

**C. Transactional-isolation oracles — the verdict vocabulary A speaks.** The consistency spectrum has `linearizable ⊋ sequential ⊋ monotonic_reads` ([oracle/linearizability.py](src/forze_dst/oracle/linearizability.py)) but `snapshot_isolation` / `serializable` are missing — they need transaction read/write-set recording the trace does not yet capture. C records those sets and adds the oracles, so "did this run violate snapshot isolation?" becomes answerable. **C is not a separate goal — it is the oracle A's battery uses to render its verdicts**, and the same checkers the autonomous sweep can then hunt with.

**B. Continuous simulation — run A (and the sweep) forever instead of once.** `just fuzz` exists and the `parallel_sweep`/`SimulationSeedRunner` substrate is built, but the flagship "Forze passes its own simulation" scenarios run at ~20 fixed seeds once per build, the regression corpus is empty, and no CI job runs any of it nightly. Wire the flagship scenarios through wide sweeps, seed the corpus from `FailureBundle`s, and stand up the nightly matrix + corpus-as-merge-guard.

**D. Commutativity assertions (optional, RedBlue-lite). ✅ Landed.** A declared-commutative operation that isn't actually order-independent becomes a first-class DST finding — a cross-history convergence check over a schedule band (`commutative_convergence`), with the declaration on the operation descriptor.

A is the spine. C is A's oracle. B is what makes A and the sweep run forever. D is a near-free extra. The engine is untouched; the only new *recording* surface is C.1 (read/write sets), sim-gated.

## 2. Motivation

### 2.1 The mock is the oracle's whole world (the keystone gap)

The mock is high-fidelity: its MVCC implements *true SSI* ([`_mvcc.py`](src/forze_mock/adapters/_mvcc.py) buffers an as-of-begin snapshot, rejects write-write under `SNAPSHOT` — first-committer-wins, lost-update-free — and *additionally* rejects read-write and predicate/phantom conflicts under `SERIALIZABLE`, raising `exc.concurrency(code="serialization_failure")`). The shipped write-skew slice proves the mock *distinguishes the two levels exactly as Postgres should*. **But that is the mock checking the mock.** Two documented boundaries make the gap concrete:

- *"DST is only as honest as the mock"* — if the mock and Postgres disagree on an anomaly, DST gives false confidence with no signal.
- *"The port is the oracle's horizon"* — logic *below* a port (triggers, generated columns, CHECK constraints, cascade deletes, partial indexes, LISTEN/NOTIFY) is invisible; an invariant a trigger maintains false-passes under the mock.

A second, quieter gap rides the same seam: **capabilities are self-attested.** An adapter declares its `TxCapabilities.isolation` set and the kernel fails closed against it at resolve — but nothing checks that an adapter advertising `SERIALIZABLE` actually *is* serializable rather than snapshot-masquerading. A wrong capability declaration is a silent correctness hole exactly where the framework promises a fail-closed guarantee. Conformance is the only thing that turns a self-attested ceiling into a verified one.

The "verify the mock" arc already started — the driver settled in [`forze.testing`](src/forze/testing/interleaving.py), the write-skew slice exists, the test namespace `test_forze_conformance` is reserved. **What is missing is the differential and the equivalence relation that makes a differential trustworthy.**

### 2.2 Why scope to isolation (and why the broad matrix is a trap)

It is tempting to frame conformance as "prove the mock matches every real adapter for every port." Resist it. A differential suite's real engineering content is its **equivalence relation** — the precise statement of what "the same behavior" means — and that relation is *bespoke per behavior-family*:

- isolation has one: the Adya G-phenomenon verdict at the declared level (§4.A.2), and the mock already models it;
- cache TTL, idempotency replay, queue redelivery semantics, dlock fencing, storage `head`/`copy`/range — each would need its *own* allowed-divergence vocabulary that **does not exist today**.

Differential suites that skip this die predictably: engine null-ordering, JSON-shape operators, Firestore non-native ordering, abort-vs-block, error-code text — none are bugs, all trip a naïve comparator, and the suite gets muted. **Isolation is the one family where the equivalence relation is well-understood, the mock already models it, and the existing Conductor + `TxCapabilities` line up.** Ship that. Treat any extension beyond isolation as gated on first writing that family's allowed-divergence contract — never as "turn on more comparisons."

### 2.3 The continuous-simulation harness is a stub (B)

A sharp tell: `just fuzz` finishes in under a second and selects 1 test of 353. The flagship [`test_distributed_prove.py`](tests/unit/test_forze_dst/test_distributed_prove.py) runs dlock-under-partition at `range(8)` and HLC monotonicity at `range(12)` — unmarked, so ~20 seeds once per build, never swept wider. The only `fuzz`-marked test sweeps `range(500)` over a *toy in-memory counter* that touches none of Forze's primitives. `_REGRESSION_SEEDS = ()` is empty. The `parallel_sweep` substrate ([artifacts/sweep.py](src/forze_dst/artifacts/sweep.py)) has no caller outside its own unit test. There is no CI job. The engine is flagship-grade; the *campaign* around it does not exist — and once A lands, B is what runs the conformance battery and the sweep forever rather than once.

### 2.4 No transactional-isolation oracle in the sweep (C)

[`oracle/linearizability.py`](src/forze_dst/oracle/linearizability.py) ships single-object models (`linearizable`, `sequential`, `monotonic_reads`). The *transactional* anomalies — lost update, write skew, read skew, phantom — are defined over a transaction's **read set and write set**, which the trace does not record. So write skew is catchable today *only* via a hand-built forced interleaving (A), never as a sweep invariant the fuzzer can hunt. C records the sets and adds the oracles, giving A its verdict vocabulary and the autonomous loop its database-correctness properties in one move.

## 3. Goals / Non-goals

**Goals.**
- A shippable conformance capability: the Adya anomaly battery + a real-adapter (testcontainers) runner asserting *mock ≡ real* per `IsolationLevel`, **with a first-class, reviewed allowed-divergence catalog**.
- A **faithful mock read-committed** (no dirty reads) so the default isolation models the real engine — closing the verified write-through gap before the differential runs (§4.E).
- Verification that an adapter's self-attested `TxCapabilities.isolation` matches its observed behavior.
- Transactional-isolation invariants (`snapshot_isolation`, `serializable`, optionally `causal`) over recorded read/write sets — the battery's verdict oracle and a new sweep-declarable property.
- The flagship distributed scenarios swept wide (`fuzz`-marked), seeding a real regression corpus; a nightly CI matrix with the corpus as a merge guard.

**Non-goals.**
- **The general "mock ≡ real for every port" matrix.** Explicitly out (§2.2). Only the isolation family is in scope; extension is gated on first authoring the target family's allowed-divergence contract. This is the discipline that keeps the suite alive.
- **Comparing mechanism, not outcome.** Error codes/SQLSTATE, abort-vs-block, victim identity, lock granularity, and timing are *allowed divergence* (§4.A.4) — never assertion targets.
- **Full DST against real backends** (real Postgres under virtual time). Real I/O is non-deterministic and breaks the replay guarantee; the conformance *differential* is the correct, honest substitute. "Real-adapter DST" must not become a goal.
- **Teaching DST about below-the-port logic** (triggers, generated columns). The oracle's horizon stays the port; the real-adapter tier covers what the mock structurally cannot *for the anomalies the battery exercises*, and the boundary is documented, not erased.
- **New schedulers/engines.** Random + PCT + DPOR + Hypothesis + coverage-guided is already beyond SOTA.
- **RedBlue / multi-master consistency.** No active-active substrate exists. Workstream D borrows only the commutativity-as-verifiable-hint slice, not the replication model.
- **Redis on the anomaly matrix.** `MULTI/EXEC` is atomic batching + optional `WATCH` CAS, not an ANSI/Adya isolation level; it is modeled as "serialized command batch + optional CAS," never run through the battery.

## 4. Design

### 4.A The keystone — conformance

#### A.1 The forced-interleaving substrate (shipped)

[`Conductor` / `Gate`](src/forze/testing/interleaving.py) (asyncio + attrs only, zero DST/forze coupling) already turns a normally-racy multi-transaction scenario into a **deterministic** one: each participant parks at `gate.checkpoint()`; the `Conductor` releases participants one step at a time in an explicit `schedule`, so only one runs at a time and the interleaving is exactly the schedule — reproducibly, on the mock *or* a real database. This is the engine of the battery and it needs no changes. The write-skew slice already drives two contexts over one shared `MockState` through `Conductor(schedule=("A","A","B","B"))` and reads the post-run verdict; every anomaly case is the same shape with a different schedule and a different expected per-level outcome.

#### A.2 The anomaly battery (Adya G-phenomena, intent-named levels)

A fixed table of classic isolation anomalies, each a forced `Conductor` schedule with a **known verdict per `IsolationLevel`**. We use **Adya's cycle-based (G-) phenomena**, not the ANSI/Berenson preventative (P-) phenomena: the P-definitions describe lock-based mechanisms and over-restrict (they forbid legal MVCC executions), while the G-definitions describe the actual correctness property and are the right oracle for a multi-version/optimistic engine like the mock and like Postgres.

Forze models three intent-named levels ([`IsolationLevel`](src/forze/application/contracts/transaction/ports.py), `READ_COMMITTED < SNAPSHOT < SERIALIZABLE`); the adapter maps each to its backend spelling (`SNAPSHOT` → Postgres `REPEATABLE READ` = true snapshot isolation; `SERIALIZABLE` → Postgres SSI; `SNAPSHOT` → Mongo `readConcern:"snapshot"`; Mongo has *no* serializable level). The expected verdict matrix over Forze's three levels (PERMIT = the anomaly can occur; PREVENT = guaranteed not to, whether by abort or by block):

| Anomaly (Adya) | `READ_COMMITTED` | `SNAPSHOT` | `SERIALIZABLE` |
|---|---|---|---|
| Dirty write (G0) | prevent | prevent | prevent |
| Dirty / intermediate read (G1a, G1b) | prevent | prevent | prevent |
| Circular information flow (G1c) | prevent | prevent | prevent |
| Observed-transaction-vanishes (OTV) | prevent | prevent | prevent |
| Non-repeatable read (P2) | **permit** | prevent | prevent |
| Lost update (P4) | **permit** | prevent | prevent |
| Read skew (G-single) | **permit** | prevent | prevent |
| Phantom, read form (PMP) | **permit** | prevent | prevent |
| **Write skew (G2-item)** | permit | **permit** | **prevent** |
| **Read-only transaction anomaly (G2, 3-txn)** | permit | **permit** | **prevent** |
| **Predicate write cycle (G2)** | permit | **permit** | **prevent** |

(Forze has no `READ_UNCOMMITTED`, so dirty read is prevented at its weakest level.) The three bottom rows — the SI↔serializable gap — are the highest-value cases and exactly what the shipped write-skew slice already exercises; the mock's `_mvcc.py` distinguishes them via read-write + predicate/scan conflict detection. Each case is parameterized by adapter and `IsolationLevel` and asserts the level's promised verdict; the verdict oracle *is* the C checkers (A.3).

#### A.3 The verdict oracle — normalize, then compare (the actual product, part 1)

The differential's core is **not** "run it twice and `==` the results." It is a deliberate **equivalence relation** that compares only the property that matters:

- The oracle is the **Adya G-phenomenon verdict at the declared level**, computed from the *observed history* (a DSG-cycle check over the recorded read/write sets from C.1), parameterized by the engine's declared snapshot/serializable semantics class.
- **All "prevented" mechanisms normalize to one `PREVENTED` verdict before comparing** — abort (`serialization_failure`/`40001`), block-then-proceed, deadlock-abort, lock-wait. The mock prevents by abort; a lock-based engine may prevent by blocking; both are correct.
- The comparison is `mock_verdict == real_verdict` over the normalized `{PERMITTED, PREVENTED}` outcome — **never** over error code, error text, which transaction was the victim, or timing.

A *real disagreement* (a bug in the mock or a lie in the adapter's capability) is: an anomaly **occurs at a level whose contract forbids it** (write skew at `SERIALIZABLE`, read skew at `SNAPSHOT`, lost update at `SNAPSHOT`), or a level **silently strengthens** beyond its contract in a way code relying on the weaker contract would miss (flagged for review, not auto-failed). Everything else is A.4.

#### A.4 The allowed-divergence catalog (the actual product, part 2)

A first-class, version-controlled, **reviewed** artifact — the false-positive firewall that decides whether this suite survives contact with real engines. It enumerates differences that are *expected and correct*, and the suite must treat each as non-failing:

1. **Abort vs block on conflict** — SSI aborts the loser; lock-based engines block then proceed or deadlock-abort. Same prevention.
2. **Error code / SQLSTATE / message** — PG `40001`, MySQL `1213`/`1205`, Oracle `ORA-08177`. Match the *class* "retryable serialization failure," never the literal.
3. **Victim identity** — first-committer-wins vs first-updater-wins vs deadlock-victim heuristics decide *which* txn aborts; non-deterministic, never asserted.
4. **`REPEATABLE READ` semantics class** — RR-as-SI (Postgres: abort-based, no phantoms, prevents lost update) vs RR-as-next-key-locking (MySQL InnoDB: block-based, permits some write-predicate anomalies). *Legitimately different guarantees under the same SQL name* — the expected matrix is parameterized by the engine's declared class; a mismatch is allowed only while both stay within their documented contract.
5. **Predicate / range-lock granularity** — gap-lock width, SSI's conservative (false-positive) aborts. *Extra* prevention is still correct; only *missing* prevention is a bug.
6. **Snapshot timing** — statement-snapshot (RC) vs transaction-snapshot (SI/serializable); BEGIN-time vs first-read-time. Changes intermediate visibility, not the level's anomaly verdict.
7. **Conflict-detection timing** — eager (mid-transaction) vs lazy (validate-at-commit). Same final verdict.
8. **Category mismatches** — Mongo is SI, not serializable (do not assert write-skew prevention against it); Redis is off the matrix entirely.

The rule the whole suite obeys: **assert the normalized anomaly outcome at the declared level; treat every entry above as allowed.** Adding a backend means first reviewing and extending this catalog — that review *is* the work, and pretending otherwise is how the suite gets disabled.

#### A.5 The real-adapter differential + capability verification — ✅ Postgres landed 2026-06-25

Runs the identical battery against real **Postgres** via testcontainers (`test_pg_isolation_conformance.py`), over a pooled client so each session is an independent connection — a genuinely concurrent transaction forced into an exact interleaving by the `Conductor`. The assertion is differential per A.3: both the mock and Postgres are asserted against the *same* `expected_verdict`, so green = **mock ≡ real** for the isolation family (`SNAPSHOT`→`REPEATABLE READ`, `SERIALIZABLE`→SSI). This also verifies the otherwise self-attested `TxCapabilities` (the Postgres manager advertises all three levels; every battery row each promises passes against the real engine). The conformance context wires a **passthrough resilience executor** so OCC retry doesn't fire — the differential tests the isolation layer, not the app's retry policy (a forced conflict must surface, not be retried inside the poisoned transaction).

**Findings the differential surfaced** (its whole point): the rev-conflict **exception contract** diverged — the mock raised `CONCURRENCY` ("Revision conflict") while every real adapter (the shared persistence gateway) raises `PRECONDITION`/`revision_mismatch`. **Fixed 2026-06-25:** the mock (the outlier) now raises the identical `exc.precondition("Revision mismatch", code="revision_mismatch")`, so an app's optimistic-concurrency handling behaves the same on the mock as on every real backend (§9.11 resolved).

**Mongo leg ✅ landed 2026-06-25** (`test_mongo_isolation_conformance.py`): the same battery, run against a real Mongo **replica set** (testcontainers) at `SNAPSHOT`, all green — **mock ≡ real Mongo** for snapshot isolation (write skew permitted at snapshot, no SSI — the SI category). Mongo's `TxCapabilities` advertises only `{READ_COMMITTED, SNAPSHOT}` (no serializable), and the differential runs at `SNAPSHOT`. Finding (asserted, not assumed): Mongo's `READ_COMMITTED` *inside a transaction* is **snapshot-isolated** — a non-repeatable read is PREVENTED even at `READ_COMMITTED`, because a Mongo transaction reads a consistent snapshot regardless of read concern — so on Mongo `READ_COMMITTED` is not a distinct weaker level (a documented characteristic, not a bug).

#### A.6 Package home (open — see §9.1)

The reserved top-level name `forze_conformance` is **not** a settled decision and is probably the wrong shape. The capability is testing/simulation tooling for the same audience as DST, so the leaning home is a **`forze_dst` submodule** (e.g. `forze_dst.conformance`), reachable via the existing `dst` extra — one "correctness tooling" home rather than a near-empty new top-level package. The general interleaving primitive stays in [`forze.testing`](src/forze/testing/interleaving.py) (core, zero deps) so any test can use it; the battery + real-adapter runner + allowed-divergence catalog import it. **Resolved in P1: shipped as `forze_dst.conformance`** (a `forze_dst` namespace), the design otherwise home-agnostic (§9.1).

#### A.7 What conformance does NOT claim (the honesty boundary)

Stated plainly so the guarantee is never oversold: (a) the oracle's horizon stays the port — below-the-port app-specific logic (triggers, generated columns) is covered by the real-DB tier **only for the anomalies the battery exercises**, not in general; (b) the equivalence relation is bespoke to the isolation family and does not generalize for free; (c) `SNAPSHOT` is genuine snapshot isolation, *incomparable* to ANSI Repeatable Read (it permits write skew, prevents read-form phantoms) — the matrix encodes this rather than pretending a clean ladder; (d) conformance proves *mock ≡ real for the modeled anomalies at the declared level*, which is exactly what makes downstream DST claims honest — and nothing more. Until conformance lands for a given backend, downstream verdicts that depend on it must be stamped **"verified against mock substrate."**

### 4.B Operationalize continuous simulation

**B.1 Wide-sweep the flagship scenarios. ✅ Landed 2026-06-25.** The dlock and HLC scenario *bodies* moved to [`tests/support/dst_flagship.py`](tests/support/dst_flagship.py) as top-level **picklable** `run_dlock_seed` / `run_hlc_seed` → `SeedOutcome` targets (a closure couldn't cross the process boundary; a function in a test module is risky to re-import in a worker, so a clean support module). `fuzz`-marked `TestFlagshipFuzz` drives them through `parallel_sweep` over wide bands (verified: the process pool runs them, no violations). The point-in-time `range(8)`/`range(12)` smoke tests stay. **Reachability is now folded into the sweep (§9.12a, landed 2026-06-26):** `SeedOutcome.reached` carries each run's reached labels, `_aggregate` folds per-label run counts into `SweepResult.reached_runs`, and `SweepResult.reachability(targets)` returns the cross-sweep `ReachabilityReport` — so both the corpus and the wide fuzz now assert `result.reachability(TARGETS).satisfied` (the dangerous interleaving fired across the band), not just that no invariant tripped. A green sweep that never raced was the precise false-confidence hole this closes; the HLC corpus in particular gains a real non-vacuity signal (it has no behavioural coverage, being register-based). *Note:* the flagship are `Cluster` / `run_recorded` scenarios, not single-node `Simulation`s, so they need their own `run(seed)` targets — `SimulationSeedRunner` is `Simulation`-only (and does not track reachability — its `SeedOutcome.reached` is empty, which the fold treats as inert).

**B.2 Seed the regression corpus. ✅ Landed 2026-06-25.** `TestFlagshipCorpus` runs the flagship over a fast band plus `*_REGRESSION_SEEDS` (in `dst_flagship.py`) **every build** via `sweep` (sequential, fast) as a merge guard. The regression tuples are empty today (the flagship is correct — no found bug), and the documented mechanism is "append any seed that ever found a bug." Reproduction is by **deterministic seed** (the cluster/`run_recorded` scenarios re-run identically at a seed); the `FailureBundle` / `replay_bundle` machinery ([artifacts/bundle.py](src/forze_dst/artifacts/bundle.py)) is `Simulation`-shaped and remains the path for single-node `Simulation` sweeps. The toy meta-test corpus in `test_dst_corpus.py` (oracle-sensitivity, not Forze primitives) is unchanged.

**B.3 Nightly matrix. ✅ Landed 2026-08-13.** [`.github/workflows/nightly.yml`](.github/workflows/nightly.yml) + [`dst_nightly.py`](.github/scripts/dst_nightly.py) + `just dst-nightly` / `dst-nightly-cells` / `dst-nightly-all`. The corpus was already the merge guard (B.2); this is the other half.

**The fault-profile axis had to be built first** — it did not exist. `dlock_config` hardcoded one partition window and one error rate, so "× fault-profiles" had nothing to range over. `FaultProfile` now declares an environment (isolated nodes, window, link loss, error rate), and four ship: `baseline` (the historical shape), `contention` (no partition, no faults — a violation there is the lock itself, with no infrastructure to blame), `flaky-link` (`loss=0.5`, the partial-drop path nothing previously exercised) and `storm` (two of three nodes cut, 70% errors).

**Each profile carries its own reachability targets, and an empty set is refused.** Which dangerous states are reachable is a property of the environment, not of the scenario: `contention` can never drive `write-retried` because no call can fail under it. A shared target set would fail that profile every night; a profile declaring *no* targets would pass vacuously forever, including on the night the scenario stopped racing — which is the failure mode the reachability fold (§9.12a) exists to prevent, reappearing one level up.

**Sizing, measured rather than assumed.** This phase read "ops-gated" for two months on the belief that a nightly is expensive. It is not: a seed costs ~0.85 ms through the process pool, linear from 256 to 65,536. The merge guard's 64-seed dlock band is a third of a second of searching — so the nightly runs **65,536 seeds per cell, 1024×**, and the full matrix is 327,680 seeds in ~3 minutes locally. A nightly running a band a PR could have run is a nightly that finds what the PR already found.

**The cell list is derived from the profiles, not written down.** `--matrix` emits it, the workflow fans out over it via `fromJSON`, and the verdict requires exactly it — one list, so a dropped profile cannot pass at both ends. The verdict refuses a missing cell, a band that ran zero seeds, any violating seed (named, with the `*_REGRESSION_SEEDS` tuple to append it to), a declared target the band never drove, and a result for a cell nobody declared. It reads JSON through the standard library alone, so the gate cannot fail for want of an extra.

*Not built: a trend store.* Each night's results are an artifact kept 90 days, so reachability rates and behaviour counts are comparable across nights by reading them — there is no service accumulating the series, and calling that a "trend artifact" would overstate it.

### 4.C Transactional-isolation oracles (A's verdict vocabulary)

**C.1 Per-event transaction-id seam. ✅ Landed 2026-06-25.** The trace records each port call's entity `key` and `tx_depth` but **not a transaction identity**, and the obvious shortcut — attribute each keyed call to the operation span containing it — is **unsound under interleaving** (verified: concurrent operations interleave at every `await`, spans overlap, and an outer call landing inside an inner span is misattributed). So sound attribution uses a **per-event `tx_id`**: a `ContextVar` on `TransactionContext` (alongside `__tx_depth`) minted at root scope enter from a **run-global counter** (`bind_tx_sequence` / `next_tx_id` in [tracing/emit.py](src/forze/application/execution/tracing/emit.py), bound once per run in `run_recording` — the §9.10-resolved choice, unique across all execution contexts sharing one trace buffer), threaded to the port proxy via the sibling wiring seam `tx_id_getter=ctx.tx_ctx.tx_id` at [port_instrumentation.py](src/forze/application/execution/deps/port_instrumentation.py), carried on `TracingEvent`, and folded into the history. It is an int (PII-free), deterministic under replay (enter order is deterministic), and `None` in production (no counter bound → zero cost; ports aren't even wrapped). Optional value-level capture rides the already-shipped `capture_values` gate.

**C.2 The invariants. ✅ Landed 2026-06-25** ([oracle/isolation.py](src/forze_dst/oracle/isolation.py)) — the **sound kernel** as pure functions over explicit `TxRecord` read/write sets:
- `find_snapshot_isolation_violations` — no write-write conflict between concurrent committers (lost-update-free).
- `find_serializable_violations` — additionally no two-transaction write-skew anti-dependency (each read a key the other wrote); strictly a superset (`serializable ⊋ snapshot`).
- Sound and incomplete (catches the canonical two-transaction key-level anomalies; predicate phantoms and ≥3-transaction cycles need scan tracking / version order — deferred, like `monotonic_reads`'s posture). `causal` remains an optional follow-up.

Shipped both as **pure detectors over `TxRecord`** (the kernel) and — now that C.1 lands — as `History`-reading, sweep-declarable `Invariant`s (`snapshot_isolation()` / `serializable()`) that derive the read/write sets from the trace via `transactions_from_history` (grouped by `tx_id`). The 3-transaction read-only anomaly, predicate phantoms, and `causal` remain deferred follow-ups.

These compose with the register-history checkers (`serializable ⊋ snapshot_isolation`), become declarable in any sweep config, and give the fuzzer (B) and the battery (A) **one verdict vocabulary**.

**C.3 Close the loop with A.** Once `serializable`/`snapshot_isolation` exist as oracles, the battery's verdict oracle (A.3) *is* these checkers — the same code asserts "the mock obeys its declared level," "the real adapter obeys its declared level," and "a sweep run didn't violate isolation." One isolation model, three consumers.

### 4.D Commutativity assertions (optional, RedBlue-lite) ✅ Landed 2026-06-26

Full RedBlue is a non-goal (no multi-master substrate, nothing produces a red/blue classification). But one cheap, useful slice fits *this* RFC: a handler/operation may declare itself **commutative** (a boolean hint on the freeze-time operation descriptor that already carries `kind`, `deadline`, `supports_idempotency_key`). DST then asserts it: two interleavings of the same workload involving the commutative op must converge to **identical final state**. It reuses the existing PCT/DPOR exploration (the scheduler already drives the order permutations) and bit-exact replay (the diverging schedule seed reproduces the counterexample). A declared-commutative op that *isn't* order-independent becomes a first-class finding — the safety half of RedBlue's value, with zero commitment to replication. The hint feeds DST verification only; no execution path consumes it. Lowest priority; ship only if a real handler wants the guarantee.

**What shipped.** `OperationDescriptor.commutative: bool = False` is the declaration; `forze_dst.invariants.commutative_convergence(build, *, final_state, schedule_seeds, seed=0)` is the verifier. It calls `build()` once per schedule seed for a *fresh* scenario (the no-shared-mutable-state rule of `Build`, since the workload runs many times — a single reused scenario closure accumulates state across runs, a footgun the API design avoids by taking a factory), holds the input `seed` fixed so only the scheduler permutes the interleaving, and compares each run's `final_state(history)` signature. One `Violation` per distinct extra end state, each naming the reproducing schedule seed.

**One correction to the original framing.** This is a **cross-history** checker, *not* a single-`History` `Invariant`: commutativity is a relation *across* interleavings (one history is one ordering and proves nothing alone), so it cannot be an `Invariant(History) -> [Violation]` the way `snapshot_isolation`/`serializable` are — it must rerun. Sound (a divergence is a genuine counterexample) and incomplete (only the interleavings the band reaches are tried — widen it, or drive it from the coverage-guided explorer, to hunt harder). The original note that it reuses "C.1 read/write-set recording (compare end-states by touched keys)" overstated the coupling: the end-state signature is a caller-supplied projection of the history (touched-key values *if the caller wants*, but any hashable end state works), so the checker does **not** depend on the C.1 tx-id seam.

### 4.E Mock fidelity — faithful read-committed + retiring the no-op footgun (prerequisite for the differential)

The differential (A.5) is only as honest as the mock it compares against. Two mock-fidelity gaps must close *before* the real-adapter leg, or the differential either fails for an embarrassing reason or tempts a dishonest divergence entry.

**E.1 Faithful read-committed. ✅ Landed 2026-06-25.** The default mock transaction manager was **write-through**: a write landed in the live store immediately, so a concurrent transaction could read another's not-yet-committed write (verified: a reader observed `99`, an uncommitted value the writer then rolled back — a **dirty read**). Real Postgres read-committed never does this, so the mock was *weaker than read-committed* at the default level — a source of DST false positives impossible on real Postgres, and a disagreement the P4 differential could not honestly file as allowed divergence. The fix reuses the MVCC machinery (`forze_mock/adapters/_mvcc.py`): every level now **buffers document writes to an overlay and publishes at commit**, so the live store holds committed rows only and no transaction observes an uncommitted write. Levels differ only in reads — read-committed reads through to the live store (latest committed per statement, so non-repeatable reads / read skew remain permitted), snapshot/serializable read a frozen as-of-begin snapshot. **Subtlety found and handled:** simply skipping commit-validation for read-committed was wrong — it let two concurrent rev-guarded updates both commit (a double-charge in `dst_payments`), because the mock's rev-OCC relied on write-through visibility. Postgres read-committed prevents this via row-locking + the stale-rev guard, so faithful read-committed must reject a **write-write conflict for rev-guarded writes** (first-committer-wins), while leaving a *blind* (rev-less) write to lose silently as the textbook permits (`MvccTx.rev_guarded` tracks which writes were rev-guarded). The undo journal now covers only the non-document stores (outbox/inbox/identity). The conformance `dirty_read` case proves it (prevented at every level); the full 7956-test unit suite is green (two tests that asserted the old write-through behavior were updated to the faithful behavior).

**E.2 Retire the no-op manager — reconsidered and declined.** The plan was to remove `transactions="none"` as a wiring footgun. On closer analysis the premise does not hold: `MockDepsModule` is the in-memory mock, used only in tests/dev/DST and **never deployed**, so `transactions="none"` is not a *production* footgun — and its docstring already says it is "only for tests that deliberately assert that unfaithful behavior." Meanwhile it has three legitimate, current uses: it is the *only* mock manager reporting limited (read-committed-only) capabilities, which `test_operation_declared_isolation_beyond_caps_fails_closed_end_to_end` relies on to prove a fail-closed `SERIALIZABLE` rejection; it is the minimal manager the SQS/RabbitMQ envelope-tracing integration tests wire directly via the `mock_txmanager` factory; and `test_dst_payments` uses it for the pedagogical contrast that shows *why* faithful transactions matter (the no-op surfaces a false double-charge the faithful default does not). Removing the option would break the contrast test and add friction to the others for no safety gain. **Verdict: keep it.** The footgun framing was overstated for a test-only mock; the documented default (`"journal"`, now faithful at every level after E.1) is the safe path, and `"none"` is an opt-in, clearly-labelled test affordance.

## 5. Phasing

Ordered by the keystone path — each lands usefully, and the conformance spine comes first.

- **P1 — A.1/A.2 battery (mock-only) + A.4 allowed-divergence catalog v0. ✅ Landed 2026-06-25** (`forze_dst.conformance`). The Adya battery on the shipped Conductor against the mock — `non_repeatable_read` / `read_skew` (RC↔SNAPSHOT boundary), `write_skew` (SNAPSHOT↔SERIALIZABLE boundary), `lost_update` (the rev-OCC strengthening) — plus the allowed-divergence catalog (`CONTRACT_STRENGTHENINGS` / `MECHANISM_DIVERGENCES`) authored from the start. The battery is adapter-agnostic (a `ConformanceBackend` seam; the mock backend lives in the test) and the verdict normalizes to permitted/prevented, so P3 only adds a real backend. A `test_any_deviation_from_contract_is_registered` test enforces no-silent-divergence. *Not yet built:* phantom/predicate (G2) and the 3-txn read-only anomaly (need predicate scans / a third session — harness already supports them).
- **P2 — C.1/C.2 transactional oracles. ✅ Landed 2026-06-25.** C.1 = the per-event `tx_id` seam (run-global counter → `TransactionContext` → port proxy → `TracingEvent` → projection); C.2 = `snapshot_isolation` / `serializable` as both `TxRecord` detectors and sweep-declarable `History` `Invariant`s. Sound (tx_id grouping, not operation-span) + tested (kernel, derivation incl. interleaved case, real-run e2e). Deferred follow-ups: 3-tx read-only anomaly, predicate phantoms, `causal`.
- **P3 — mock fidelity. ✅ E.1 landed 2026-06-25; E.2 declined.** E.1: read-committed now buffers document writes through the MVCC overlay (no dirty reads at any level), with rev-guard-aware write-write conflict so concurrent rev-guarded updates can't both commit while a blind write still loses silently; the `dirty_read` battery case proves it; full suite green. E.2: keep the no-op manager (§4.E.2 — not a production footgun for a test-only mock; legitimate test uses).
- **P4 — A.5 real-adapter differential (Postgres) + capability verification. ✅ Landed 2026-06-25.** The mock≡real assert via testcontainers (all green); the self-attested `TxCapabilities` is now verified against the real engine. **The flagship deliverable.** Surfaced one finding (rev-conflict kind divergence — §9.11). Mongo (SI-only) leg + the broader anomaly cases are follow-ups.
- **P5 — B.1/B.2 wide-sweep wiring + corpus. ✅ Landed 2026-06-25.** Flagship bodies → reusable picklable seed targets (`tests/support/dst_flagship.py`); `fuzz`-marked wide sweep via `parallel_sweep` (verified over the process pool); a fast regression corpus runs every build as a merge guard. B.3 (nightly CI YAML) followed on 2026-08-13. **Reachability-in-sweep landed 2026-06-26** (`SweepResult.reachability(targets)`; corpus + fuzz now assert the dangerous interleaving fired, §9.12a); a single-node `Simulation` flagship for the `FailureBundle` path remains a follow-up (§9.12b).
- **P6 — Mongo SI conformance leg ✅ landed 2026-06-25** (`test_mongo_isolation_conformance.py`; mock ≡ real Mongo at `SNAPSHOT`). **B.3 nightly CI matrix ✅ landed 2026-08-13** (§4.B.3): the fault-profile axis it needed, four environments, 65,536 seeds a cell, and a verdict that refuses an empty band as loudly as a violating one. Remaining P6: the `causal` oracle, as a follow-up.
- **P7 (optional) — D commutativity assertions. ✅ Landed 2026-06-26.** The `OperationDescriptor.commutative` declaration hint + `commutative_convergence` (a cross-history checker, not the single-history `Invariant` the original framing implied — §4.D), with a unit demonstration (disjoint writes commute; last-writer-wins on a shared cell diverges and is reported). Independent of the C.1 tx-id seam (the end-state signature is a caller-supplied history projection). Full DST suite + quality gates green.

P1+P2 are the substance; **P3 makes the mock faithful so the differential means something**; P4 is the payoff; P5+ make it permanent. (Note: B was previously framed as the cheapest first move — it is demoted because a wide sweep with no real-adapter oracle still only proves things about the mock; the keystone value is A, so A leads. P3 is sequenced before P4 deliberately: a differential against an unfaithful mock either fails embarrassingly or pressures the catalog to absorb a real bug.)

## 6. Alternatives considered

- **Run real DST against live Postgres.** Rejected (non-goal): destroys determinism/replay. The differential gives the trust without the loss.
- **The broad "mock ≡ real for every port" matrix from day one.** Rejected (§2.2): no shared equivalence vocabulary; dies of false positives; would need a new contract layer. Isolation only, extension gated.
- **Compare runs by equality of results/errors.** Rejected: error codes, victim identity, abort-vs-block, and timing differ legitimately; the equivalence relation (A.3/A.4) is the whole point.
- **Keep isolation checks only in the forced-interleaving harness.** Rejected: hand-authored schedules can't *find* anomalies the way the sweep can; C makes them first-class so the fuzzer hunts them.
- **A bytecode/SQL-level model of the real DB.** Rejected: enormous, brittle, still not the real engine. Testcontainers runs the actual engine.
- **A new top-level `forze_conformance` package.** Rejected (§4.A.6, resolved in P1): a `forze_dst.conformance` submodule keeps one correctness-tooling home and avoids a near-empty top-level package the maintainer dislikes.
- **Fix the mock dirty read by making SNAPSHOT the default isolation instead of repairing read-committed.** Rejected (§4.E.1): SNAPSHOT is *too strong* for the default (it prevents non-repeatable reads, which read-committed should permit), so it trades one infidelity for another and would mask real RC behavior. Repair read-committed to be faithful read-committed; keep the default at the level apps actually run.
- **Leave the mock dirty read and document it as a known divergence.** Rejected (§4.E.1): it is a fidelity bug, not a mechanism difference, so filing it as allowed divergence would be the exact dishonesty the catalog discipline (§9.4) forbids — and it would keep producing DST false positives at the default isolation.

## 7. Relationship to what's already shipped

- **Reuses, doesn't rebuild:** the `forze.testing` Conductor/Gate driver + the write-skew slice; the mock's true-SSI MVCC; `parallel_sweep`/`SimulationSeedRunner`; `FailureBundle`/`replay_bundle`/corpus; `coverage()` reachability aggregation; `capture_values` + redaction; the register-history checkers; the `TxCapabilities`/`IsolationAware` capability contract.
- **Shared with the self-hosted durable execution tier:** that plane also leans on the conformance harness and a DST crash/recovery fault; its Postgres step-journal would be conformance-tested against the same testcontainers fixtures — coordinate so fixtures are shared, not duplicated.
- **DST engine untouched:** no new scheduler, loop, or exploration strategy. The only new *recording* surface is C.1 (read/write sets), sim-gated.
- **One mock change (E.1):** read-committed moves from write-through to a buffered overlay (reusing the existing `_mvcc.py` machinery). This touches the mock's tx/storage routing — not the DST engine and not any contract — and is gated by a full-suite run for blast radius, since some tests may rely on write-through visibility today.

## 8. Open questions

1. **Package home for the battery + runner.** *Resolved in P1: `forze_dst.conformance`* (with the `dst` extra; one correctness-tooling home), exposed as a `forze_dst` namespace. The interleaving primitive stays in `forze.testing`. Revisit only if app authors need it without the `dst` extra (then a thin standalone re-export). The maintainer dislikes a top-level `forze_conformance`; the submodule avoids it.
2. **Package boundary for C.** Do the transactional oracles live in `forze_dst/oracle` (DST-only) or wherever (1) lands so app authors get them without the `dst` extra? *Lean: `forze_dst/oracle` with a re-export from the conformance home.*
3. **Read/write-set recording cost.** Does C.1 piggyback the recorder (sim-gated, default) or need its own opt-in flag like `capture_values`? *Lean: piggyback, sim-gated.*
4. **Allowed-divergence catalog governance.** Where does it live and how is it reviewed — a typed in-repo table next to the battery, reviewed on every backend addition? How do we prevent it silently absorbing a *real* disagreement as "allowed"? (A divergence entry should cite the engine doc/Jepsen/Hermitage result that justifies it.)
5. **RR-semantics-class parameterization.** The expected matrix is parameterized by the engine's declared snapshot/serializable class (§4.A.4 item 4). Where is that class declared — derived from the adapter's `TxCapabilities` mapping, or a separate conformance-profile per backend?
6. **Real-adapter scope for v1.** *Resolved: Postgres + Mongo both landed.* Postgres covers all three levels (RC/SNAPSHOT/SERIALIZABLE via SSI); Mongo covers `SNAPSHOT` (SI-only — its in-tx `READ_COMMITTED` is snapshot-isolated, so not a distinct level). Further engines (MySQL, etc.) gate on first authoring their RR-semantics-class entry in the allowed-divergence catalog (§4.A.4 item 4).
7. **Below-the-port coverage.** Add an explicit conformance tier for app-specific trigger/constraint logic (real DB only), or keep that in app integration tests and only document the boundary (§4.A.7)?
8. **Corpus storage.** Checked-in `FailureBundle` JSON under `tests/` (reproducible, reviewable, grows the repo) vs a generated artifact the nightly republishes? Pick before P5.
9. **Sweep budget vs. CI time.** *Resolved 2026-08-13 by measurement.* Throughput is ~0.85 ms/seed through the process pool and linear from 256 to 65,536 seeds, so the question had a much easier answer than the framing assumed: 65,536 seeds a cell is under a minute locally, and the whole five-cell matrix is 327,680 seeds in ~3 minutes. It *is* sharded across runners — one per cell — but for isolation and a legible per-cell verdict, not because throughput demanded it. The honest limit is not CI time; it is that a uniform sweep's value flattens as the band grows, so widening further buys less than adding a profile or a scenario would.
10. **No-op manager after E.2.** *Resolved: keep it as-is* (§4.E.2 — not a production footgun for a test-only mock; three legitimate test uses). Faithful read-committed is the default (the unfaithful write-through path was never a feature); the full-suite run found only two tests asserting the old behavior, both updated — the blast radius did not warrant a one-release opt-in.
11. **Rev-conflict exception-kind unification (surfaced by P4).** *Resolved 2026-06-25.* The mock raised a stale-rev conflict as `CONCURRENCY`; every real adapter (shared `gateway_mixins`) raises `PRECONDITION`/`revision_mismatch`. The mock — the outlier — now raises the identical `exc.precondition("Revision mismatch", code="revision_mismatch")`, so optimistic-concurrency handling behaves the same mock-vs-prod. The `revision_mismatch` code is the rev-OCC conflict signal on both backends; `is_serialization_conflict` recognizes it alongside `CONCURRENCY` (the serialization-failure signal).
12. **Sweep reachability ✅ (landed 2026-06-26) + cluster FailureBundles (still deferred).** *(a)* The reachability fold shipped: `SeedOutcome.reached` → `SweepResult.reached_runs` (per-label run counts) → `SweepResult.reachability(targets)` returning a `ReachabilityReport`, so the corpus and the wide fuzz assert the declared targets fired across the band (`result.reachability(TARGETS).satisfied`), closing the green-sweep-that-never-raced hole. *(b) Still open:* the flagship are `Cluster`/`run_recorded`, not `Simulation`s, so the `FailureBundle`/`replay_bundle` path doesn't cover them (they reproduce by deterministic seed instead) — add a cluster-aware bundle, or a single-node `Simulation` flagship to exercise the bundle path? Deferred; does not block P5.

## 9. Decisions

| # | Decision |
| --- | --- |
| 1 | The conformance battery and its runner live in `forze_dst.conformance` (behind the `dst` extra) — one correctness-tooling home; the forced-interleaving primitive stays in `forze.testing` so app authors get it without the extra |
| 2 | The transactional-isolation oracles live in `forze_dst/oracle`, re-exported from the conformance home |
| 3 | Read/write sets are derived from a **per-event `tx_id` seam**, not from operation spans. Span derivation was tried first and found unsound under interleaving — it is not an optimization to revisit |
| 4 | Read/write-set recording piggybacks the existing recorder and is simulation-gated; no separate opt-in flag (`capture_values` stays orthogonal) |
| 5 | The no-op transaction manager stays as-is: faithful read-committed is the default, and the three legitimate test uses outweigh retiring it |
| 6 | A mock↔real divergence is fixed **in the mock** by default; the allowed-divergence catalog is the exception, and every entry carries a cited cause. Consequence: adding a backend means adding a catalog review, not a catalog row |
| 7 | Real-adapter scope: Postgres (read-committed / snapshot / serializable) and Mongo (snapshot only — its in-transaction read-committed is snapshot-isolated, so not a distinct level) |
| 8 | Below-the-port logic (triggers, generated columns, views) is a **standing non-goal** of every simulation oracle; such invariants are routed to integration tests by name, never approximated |
| 9 | Commutativity hints are declared and DST-verified but **never consumed by execution** — a wrong hint must be a test failure, never a runtime reordering |
