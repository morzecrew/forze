# T-0057 — Derived permissions

Executing [RFC 0057](../rfcs/0057-derived-permissions-and-config-grants.md) **P1** on
`feat/derived-permissions`: the provider protocol, derived grants on `EffectiveGrants`, the union
and deny precedence in `decide`, the key check, batteries. P2 (`ConfigGrants`, the overlap
refusal, `require_permission`), P3 (the DST leg) and P4 (introspection, caching) follow.

## Plan

- `forze.application.contracts.authz`: `DerivedPermissions(granted, denied)`, a
  `DerivedPermissionRef` (key and provider name, no catalog id — D-3), the `PermissionProvider`
  protocol (`name`, `derive(principal, ctx)`), and the new `EffectiveGrants` field.
- `forze_identity.authz`: providers registered on the authz kernel config in declaration order
  and run where grants are assembled, so all three consumers — the decision adapter, the scope
  adapter and the effective-grants adapter — see the same union (D-1). `decide` refuses a denied
  key before any grant is matched (D-2), then matches the action against catalog **or** derived
  grants; derived keys also count toward the owner override, unless denied. A provider that
  raises yields a denial for its keys, never an exception past the decision (D-4).
- Batteries per §6's P1 legs: union both ways, a denial masking a direct, a role and a group
  binding (three paths through the resolver), order independence, the field separation, and a
  failing provider denying.
- Docs: the authz page section — the protocol, the union table, "gate on permissions, never on
  roles"; changelog.

Read before code: §5's rejected alternatives — synthetic `PermissionRef` ids, syncing bindings
from state, a config/catalog precedence rule.

## Decisions the spec does not settle

Three are load-bearing, and they are put to the maintainer before code:

1. **How "an unknown key fails at wiring" is checked** (§1, §4, D-6). The permission catalog is
   documents in the database — nothing declares keys in code — and `check_wiring` runs a dry run
   that reads no database (`src/forze/application/execution/operations/wiring.py:123-197`). A
   provider's `derive` is also dynamic, so nothing knows its keys before it runs.
2. **The shape of the deny set on `EffectiveGrants`** (§5.2 "one field", D-2, D-3). `decide` must
   see the denied keys, and §5.2's single `derived` field carries only grants.
3. **Which identity a provider derives for on a delegated call** (§10's first question, and the
   authz request's `subject`). Deriving for the subject alone hands an agent everything the user
   has; for the actor alone it ignores the delegation.

Decidable during execution, each owed an entry before it is taken: D-8 (the provider gets the
full `ExecutionContext`, and P1 has no fail-open declaration since D-4 is `LOCKED`); D-10
(introspection deferred to P4, as §12 already phases it); whether derived keys count toward the
owner override; and where providers are registered.

## Self-audit — 2026-09-29

Scope: the branch against `main` — the RFC 0056 close-out and 3 commits for RFC 0057 P1, 19 files,
~1k lines: the provider protocol and `EffectiveGrants.derived` in core contracts, the resolver,
policy and kernel wiring in `forze_identity.authz`, the boot check, the battery, the docs section.
Re-read RFC 0057 §5, §6 and §11 first; every P1 leg of §6 exists (the config legs are P2, the DST
leg P3).

Sabotage, then coverage: 20 mutants over `decide`, the snapshot helpers, the provider runner, the
resolver wiring, the declaration checks and the boot check. 16 killed on the first pass; the four
survivors were each untested rather than equivalent in what a reader sees:

1. **The explicit denial in `decide`** survived because `granted_keys` already subtracts denials —
   the decision was the same, the reason was not ("no grant" instead of "denied"). The reason is
   what an operator reads to learn why, so it is now pinned.
2. **A stray key recorded as granted** survived for the same reason; the snapshot would have
   shown a grant the provider was not allowed to make. Pinned on the snapshot.
3. **A key both granted and denied by one provider** was cleaned out of the grants. The cleanup
   changed nothing a decision could see, so it was deleted: the snapshot now records what the
   provider said, and the denial wins in `decide`.
4. **The boot check's tenant** was never exercised. Pinned by reading the catalog under a spy.

A fifth, pre-existing gap surfaced on the way: `decide`'s `principal_active=False` branch had no
leg anywhere; it has one now. Patch coverage then named two guards — the boot check with no
declared keys, and providers without an execution context — both pinned; 100% of added lines.

Residue I would still distrust: the mock's authz adapter does not run providers (it is a stub
beside the identity plane, not an implementation of it), so a test wired on `forze_mock` alone
does not see derived grants; a provider costs a read per decision, and nothing caches it (§8
defers that on purpose); the boot check reads the catalog under one tenant, so a catalog that
differs per tenant is checked for that tenant only.

## After the first review round — 2026-09-28

An independent review of the branch found that the per-decision half failed open in three ways
the self-audit did not reach. All three sit in the result a provider returns, which the audit
treated as well-formed:

- `DerivedPermissions(denied="ledger.write")` kept the string, so it became the set of its letters.
  The letters were stray keys and were denied, and the real key stayed granted by a catalog
  binding. The converter now refuses a string, and any key that is not a string.
- A misspelt denial did the same. Only the misspelling was denied.
- A result that was not a `DerivedPermissions` at all (`None`, a dict) raised outside the `try`.
  That crashed every decision for the principal, including actions the provider does not declare.

## Second review pass — 2026-09-28

A second independent pass over the fixed branch found a fail-open **introduced by the previous
fix**. The key-set converter checked each item with `all(...)` and then built the set from the
same value. For a one-shot iterator, the check used every item up, so a denial built from a
generator kept nothing and the catalog grant stood. The converter now materialises the value
once. Two lesser findings were fixed with it:

- A provider's `keys` is read on every decision. A mutable `set` passed the declaration check
  and could be widened after boot, past the catalog check. The declaration now requires a
  `frozenset`, which is what the protocol declares.
- The boot check named every declared key in one `$in`, and more than 1000 keys hit the query
  parser's limit with an error naming no provider. It queries in batches now.

Left for the author, not fixed here:
- the boot step is opt-in, so a deployment that omits it loses the typo check;
- `derive` has no deadline;
- the mock authz plane runs no providers.
