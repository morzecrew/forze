**Deliberately not applied:** RFC §5.5 describes the lifetime-leadership step stopping a
responsive older holder at its next renewal, with no grace on a lost lease. That step is
another RFC and does not exist yet, so the docs' "one window remains" paragraph says only what
this branch delivers: the new holder's claim is what stops an older one, so claim as the term
begins. `DistributedLockScope` keeps its behaviour (a lost lease raises at scope exit).

An acquire whose token would pass it raises `precondition` (`dlock.fence_exhausted`) without taking the lock, Redis checking the counter before `SET NX`. **Verdicts and commits.** All three accepted and fixed; each reproduced red first.

1. *Token ceiling, fixed in `da89ac976`.* Red: on `valkey:9.0`, three `INCR`s from
   2^53 − 1 returned 2^53 twice; the new battery check failed on both legs (the mock issued
   2^53, Redis a rounded token), and a Redis acquire over a counter `INCR` refuses (`5.5`, `abc`)
   left the lock key held. Fix: `ACQUIRE_DLOCK` reads the counter first and returns −1 at the
   ceiling (passed as `ARGV[3]` from `FENCE_MAX_VALUE`) before `SET NX`, and runs `INCR` under
   `pcall`, deleting the lock key again if it errors; the adapter maps −1 to `fence_exhausted`,
   a shared `precondition` coded `dlock.fence_exhausted`; the mock checks the same ceiling
   first. Battery check: MAX − 1 → one acquire draws MAX → the next is refused and the lock is
   free; advance to MAX → acquire refused. Sabotage: dropping the script's ceiling, its `DEL`,
   the mock's ceiling, or the adapter's −1 mapping each fails a test. The ceiling is one bullet
   on the Redis page and one clause on the reference page; a Fixed changelog entry records the
   key-left-held fix and the ceiling.
2. *Docs overclaim, fixed in `22af08429`.* "The store accepts it" became what holds: with the
   counter intact it is above every stored fence; after a loss the next token is above the
   fence you read, and a claim that still finds a higher fence is a refusal like any other —
   end the term and acquire again.
3. *Fixture leak, fixed in `6fd3eb82b`.* Red: a throwaway that makes the second `connect` fail
   showed `first` left open; the fixture now registers each connection's `close` on an
   `AsyncExitStack` as it opens, and the same throwaway shows it closed.
