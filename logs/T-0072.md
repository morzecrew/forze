the RFC phases it: the `FenceAdvancing` capability with its capability and spec flags, the

The author is away, so every gap below is decided here and carries a proposed row. None of
them changes what the capability does or the write rule: they settle where a check lives,
how a caller reaches the method, where the docs go and how the plane is registered. The
readiness gate (three or more load-bearing gaps) is not met on that reading.

**Deliberately not applied:** RFC §5.5 describes the lifetime-leadership step stopping a
responsive older holder at its next renewal, with no grace on a lost lease. That step is
another RFC and does not exist yet, so the docs' "one window remains" paragraph says only what
this branch delivers: the new holder's claim is what stops an older one, so claim as the term
begins. `DistributedLockScope` keeps its behaviour (a lost lease raises at scope exit).

**Findings:**

1. *Fixed (medium).* The fail-closed resolve refused a capable backend whenever the port was
   wrapped by a port proxy, so `requires_fencing_token`, and the new flag with it, could not be
   used with OTel port spans, tracing, interceptors or a resilience port policy. Pre-existing for
   fencing tokens. Reproduced red by a test, fixed by probing by attribute, logged above.
2. *Open, outside this RFC.* The same `isinstance` on a resolved, possibly proxied, port appears
   in `src/forze/application/contracts/stream/deps.py:82` (`requires_transactions`),
   `src/forze/application/integrations/graph/streaming.py:40`,
   `src/forze/application/contracts/durable/function/run_admin.py:154` and the portability
   graph-edge checks. Found by reading only; not verified, not changed.
3. *Fixed during the build (test only).* The racing-advance check first fired 40 calls at once
   and hit the integration client's 5-connection pool; it now races batches of four.
4. *Noted.* The changelog's `[Unreleased]` already carried another change's entry saying the
   example "now fences with `fence <= :token`"; its second sentence now says later writes
   accept an equal token, so the two entries do not contradict each other.

**Residue I still distrust:** the mock's advance runs under a lock, so its race check never
interleaves; only the Redis leg races for real. The loss test's two claims are gathered on two
autocommit connections: either order gives exactly one row, so it proves the outcome, not that
the two `UPDATE`s overlapped in the server. An `int` subclass with its own `__str__` (other than
`bool`) passes the bound check and would reach the script as whatever it prints.
