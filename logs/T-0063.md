# T-0063 — Per-owner write serialization and the overlap invariant

Executing [RFC 0063](../rfcs/0063-per-owner-write-serialization.md) P1–P3 on
`feat/per-owner-write-serialization`, with [RFC 0066](../rfcs/0066-storage-guarantees.md) P4
(`SerializedBy`) ahead of it on the same branch — 0063 is gated on that member existing.

Until the mapping lands, every real backend refuses the declaration, which is the state
`NonOverlapping` shipped in on RFC 0066 P1 and is the honest one: nothing claims to serialize
writes and does not. A simulation can run the rule, which is what the overlap invariant needs.

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-19T21:25:00Z
attempt: 1
claim: §4 says the declaration "serializes writes so the app's own check can be correct"; it does not follow from §5.1's rule, which takes the lock before the *write* — two handlers both read an empty relation, both decide, and serializing the two inserts afterwards lands both
evidence: tests/unit/test_forze_dst/test_write_serialization_simulation.py:1-40
action: decided
proposal: ASSUMED — the simulation asserts what the declaration gives, which is §5.3's first row: two writes for one owner never interleave. Making a read-then-write correct needs the lock taken before the *read*, and reads are explicitly never serialized (§8) — so the gap is real and belongs to the RFC rather than to this branch. The Postgres mapping, when it lands, inherits the same question.
```

Found by building the leg §5.3 asks for and watching it fail on the governed spec. The origin
application took its lock *before* its check, by hand, in the one writer that had it; a
declaration that locks at the write reproduces the serialization and not the correctness the
hand-written version got. Both rows of §5.3 are real properties and only the first is what this
member delivers.


```divergence
decision: D-8

attempt: 2
claim: the row leaves open where the lock is taken; review of the merged branch found three write paths that held an owner they never waited for — outside a transaction only the first owner was awaited, `upsert` took its owners across two awaits and missed the update's destination, and every path read its owners before waiting, so a row moved during the wait landed under an owner never taken
evidence: src/forze_mock/adapters/_document_command.py:310-362
action: decided
proposal: ASSUMED — outside a transaction a write is a statement of its own: it holds every owner it touches at once, registers like a transaction so a cycle through it is refused, re-reads its rows after every wait and takes any new owner, and gives the owners back as the call returns. A caller that decides between writes (`upsert`) decides and writes in one synchronous step rather than holding owners across a delegated call, because that call drains domain events and a handler's own transaction on the same owner would wait forever.
```


## Plan — the Postgres mapping (2026-09-25)

- `forze_postgres/kernel/gateways/write.py`: the write gateway gains the spec's `SerializedBy`
  declarations and scope, and one helper that takes `pg_advisory_xact_lock` for every owner a
  write touches, sorted, re-reading the rows after each wait until the owner set stops growing.
  Every write method calls it inside its `_write_tx()`.
- `forze_postgres/adapters/document.py`: declares `serialized_by`.
- `forze_postgres/execution/deps/utils.py`: `doc_write_gw` passes the declarations and scope.
- `forze_mock`: a refused lock cycle raises `concurrency`, the kind Postgres's deadlock takes.
- Batteries: the in-memory legs replayed on Postgres with real connections, the key parity leg,
  the cross-process key leg.
