**Finding 8 — an empty text block is an answer, not a wire defect** (coderabbitai). The
dialect refused a message whose text was empty, and the finding is that presence and
emptiness are different facts: whether the provider produced a text block is about the wire,
whether that text says anything is content, and a one-field `str` output can validly be

The truncation analogy I had been reasoning from does not carry: a cut-off completion has a

## Review round 4 — one finding, and a reachability check the reviewer got right

**Finding 9 — a `pattern` the constrained decoder cannot run** (coderabbitai, on the review
body rather than a thread). `pattern` is deliberately absent from this dialect's refused
keywords, because the provider *does* enforce it — over a subset. A pattern using a word
boundary passed wiring and would be a 400 on every request the route served.

The reviewer proposed refusing `pattern` outright until the subset is validated. Declined
that half and took the other: refusing the keyword would cost a route a constraint the
provider honours (`^INV-\d+$` is enforced natively), so the constructs outside the subset

and backreferences before a model carrying one can be built — so the reviewer's example was
the one case that could actually arrive, and the rest are checked against hand-built schemas

Pydantic's engine, not of this constraint.

## Review round 5 — a defect in round 4's fix

**Finding 10 — the escape check read one character instead of counting them**
(greptile-apps, with a harness). `\\\b` — three backslashes and a `b` — is a literal
backslash followed by an *active* word boundary, and round 4's detector looked only at the
character immediately in front of the `\b`, found a backslash there, and served the pattern.
Measured against the old code before the fix: `_UNSUPPORTED_REGEX` returned nothing for it
while returning the boundary for `\bword\b`.

The reported case is one symptom of reading a regex with four searches. An escape is decided
by **parity**, and parity is not a property of the preceding character — so the four searches
are now one left-to-right scan where an escape consumes the character after it, whatever it
is. That gets `\\\b` (refused) and `a\\bc` (served) right by construction, and it also
handles the mirror case a search cannot: `\(?=x)` is a literal `(`, not a lookahead.

One knowingly conservative call, written into the docstring: `\b` inside a character class
means a backspace and is reported as a boundary. Refusing a pattern the decoder would have
run is the safe side of that.

Two tests of mine were wrong on the way in, both by miscounting backslashes in the test
source: one written with six (an even run, correctly *served*) and one asserting that `\\(?=x)`
is inert when two backslashes pair off and leave the lookahead active. Both failed against
correct code. That is the same mistake the code made, made twice more in one sitting — and
the rule reads in two directions, which is what makes it slippery: before a `b`, an even run
leaves the letter plain; before a `(`, an odd run escapes the paren.

CodeRabbit reported the same defect independently on the summary comment, and asked for the
parity case in front of *each* construct rather than only the boundary. That was a real gap:
the scan gets them right by construction, and nothing had asserted it. Covered for the
backreference and the named backreference too.

Four mutations, four killed. 371 tests.

## Review round 7 — a class holds members, not syntax

**Finding 12 — the scanner read group syntax inside a character class** (coderabbitai).
`_unsupported_constructs` carried no class state, so `[(?=]` — a class of three characters —
was reported as a lookahead and `[(?P=]` as a named backreference. Both build in Pydantic's
own engine:

```
$ uv run python -c "from pydantic import BaseModel, Field; ..."
BUILDS '[(?=]' [(?=]
BUILDS '[(?P=]' [(?P=]
REFUSED '[\b]' SchemaError ...
```

So this was a *false refusal on a reachable path*: a route asking for a constraint the
decoder runs would have been refused at wiring. Fixed with one bit of state, which also
settles the `[\b]` residue round 5 had recorded as knowingly-left-out — inside a class an
escape spells a member, so nothing in there is a construct at all. The state ends where the
class does; without that, one `[` early in a pattern would serve every construct after it.

Two mutations (`in_class = True` on the closing branch; dropping the `not in_class` guard),
two killed. 378 tests.

One of my own new cases was wrong again, the same way: `[\](?P=n]` keeps the class open
through the spelling, while `[\]](?P=n` closes it on the second `]` and the construct is
genuinely active. The case was written the second way with the first way's docstring. The
scanner was right and the test was wrong — fourth escape-counting slip on this branch, and
every one of them has been in prose or in a test, never in the scan.

## Review round 8 — where a character class ends

**Finding 14 — a `]` in first position is a member, not the close** (greptile-apps, P2).
`[](?=foo)]` matches one of seven characters; the scan closed the class at that first `]`
and read the rest as an active lookahead. Both engines take the pattern:

```
$ uv run python -c "import re; from pydantic import BaseModel, Field; ..."
py OK   '[](?=foo)]' match )? True
  pyd OK '[](?=foo)]'
```

Fixed, together with a second rule the same question has: a POSIX class name carries a `]`
of its own, so `[[:alpha:](?=x)]` is alphanumerics plus five literal characters and both
engines take that one too. The negation marker does not count as a member, which is what
keeps the `]` of `[^]]` in first position.

Audited by differential rather than by cases. Python's own regex parser is an oracle for
what a pattern *contains* — `ASSERT`, `GROUPREF`, `AT_BOUNDARY` — so the scan can be
compared against it over a generated corpus:

```
$ uv run python - <<'PY'  # 2-, 3- and 4-piece combinations of class, escape and construct pieces
checked 15231 mismatch 77
mismatches 77 all contain '[:': True
rust accepts any of them: ['[[:alpha:](?=x)]']
```

Every divergence is the POSIX-class-name rule, and Pydantic's engine refuses 76 of the 77
patterns outright — unreachable through a model. The 77th is the one case where the two
dialects genuinely disagree, and the scan follows the engine that decides whether a model
can be built at all. Kept as evidence rather than as a test: it leans on a private stdlib
module, and the representative cases are in the battery.

Three findings in three rounds against one hand-written lexer is worth naming. All three
were *over*-refusals — a route refused at wiring with the construct named, never a pattern
sent that the decoder cannot run — so the failure mode has stayed on the safe side. If a
fourth arrives, the honest fix is to parse the pattern instead of scanning it.

384 tests.

**Drift count: 0.**
