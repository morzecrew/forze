# T-0060 — Audit spec with allowlisted metadata

Executing [RFC 0060](../rfcs/0060-audit-spec.md) P1 on `feat/audit-spec`: the contract package, the
hooks, the allowlist with both checks, a document-backed adapter exercised on the mock and on
Postgres, and the batteries of §6 except the DST leg (P2).

## Plan

- `forze/application/contracts/audit/` (new): `AuditPort` (`record(entry)`), `AuditEntry`,
  `AuditSpec` (action, allowed metadata, read rule, failure policy), `AuditOutcome`, a dep key.
  The declaration checks (a sensitive-looking key, a blank action) refuse at construction, where
  the posture's own declaration checks refuse — nothing here needs the wiring report's
  `findings` channel after all, since every check is local to the declaration.
- `forze/application/hooks/audit/` (new), beside `hooks/authz`: the step factory that binds the
  audit hooks to an operation plan, reading actor and subject from `get_authn()` (D-2), the
  allowlist check at call time (D-1), and the failure policy (D-5).
- `forze_kits/integrations/audit/` (new): the `DocumentSpec` for audit rows and the
  document-backed `AuditPort` (D-7) — a kit, since core must not own a concrete store.
- Batteries: allowlist (declared, undeclared, sensitive), outcome coverage including the guard
  denial (the D-4 leg), actor binding including a payload-supplied actor and a delegated identity,
  read rules, failure policy both ways with the business write's commit asserted; run against the
  mock and against real Postgres through the same document spec.
- Docs: a governance page section per §7, including the non-claim (no tamper-evidence); changelog.

Read before code: §5's rejected alternatives (scrub instead of allowlist, an outbox event, audit in
the adapters, `OnSuccess` + `OnFailure`) — each is a shape the implementation will reach for.

## Decisions the spec does not settle

Four are load-bearing, and three of them meet a `LOCKED` row, so this stops at the readiness gate
until the author answers them.

1. **Where the hooks run relative to the transaction** (D-4 `LOCKED`, D-5 `ASSUMED`, §6). Guards
   run in the outer scope, before the transaction opens
   (`pages/docs/recipes/authn-authz-tenancy-fastapi.md:100-104`), so only an **outer** `Finally`
   sees a denial — and an outer `Finally` runs after the transaction has committed or rolled back
   (`src/forze/application/execution/operations/run/plan.py:152-180`). One `Finally` cannot both
   see the denial and make "the business write does not commit" (§6) true when the audit write
   fails; and a `failed` row written inside the transaction is rolled back with it.
2. **Auditing a read inside a `QUERY` operation** (D-6). The whole query operation runs under the
   read-only flag (`src/forze/application/execution/operations/run/invoke.py:194-201`), and
   acquiring a command port under it raises (`src/forze/application/contracts/deps/keys.py:118-121`),
   so a document-backed audit write from any hook of a read is refused as it stands.
3. **"A principal's own data"** (D-2 `LOCKED`, D-6). §5.1 binds the subject to
   `AuthnIdentity.principal_id`, which for an undelegated call is the reader. Whose data a read
   touched is then unknowable, and every undelegated read — an administrator reading someone
   else's record included — would count as "own data" and go unrecorded.
4. **The allowlist's shape.** §5.2 declares names (`frozenset({"snapshot_id", "purpose"})`);
   §5.3 and §6 check a "scalar-typed name" and refuse "a non-scalar type" at wiring, which needs
   declared types.

Decidable during execution, each owed an entry when taken: the metadata and object-reference
callables' signatures (a failure or a denial has no result); how `denied` is told from `failed`
(the `Finally` sees only `Failure(exc)`); D-8's two halves (nesting; retry dedup, which may become
structural depending on answer 1); where the audit write's own transaction comes from outside the
business one; and the `on_failure="ignore"` warning.

## Self-audit — 2026-09-28

Scope: the whole branch against `main` — 5 commits, 21 files, ~2.1k lines (contract, hooks, kit,
unit and Postgres batteries, docs, changelog, the guards' manifests). Re-read RFC 0060 §5–§7 and
§11 first; every §6 leg exists except the DST one (P2) and the wiring-time type leg this log
departs from.

Findings, most severe first:

1. **Returning to a scope on an operation binder dropped what was bound to it** (fixed,
   `1d184d66f`). Pre-existing and outside this RFC, found because the audit binding composes onto
   the application's binder: a second `bind_outer()` kept only its own steps, so a guard bound
   first vanished without an error. Security-relevant on its own; logged above as a discovery.
2. **A denial's row was lost when the metadata callable read the result** (fixed before the first
   commit). The RFC's own example, `result.root_id`, raises for a denial, which has no result; the
   row is now kept without the metadata and the build error logged.
3. **`on_failure="ignore"` did not cover a callable that raised** (fixed before the first commit),
   and the `owner` callable on the read path bypassed the policy the same way. Both now go through
   it; a metadata refusal still raises under either policy.
4. **The audit write joined an open transaction on any route** (fixed, `7e1b7017b`). An audit
   collection on another database was written outside the operation's transaction silently; it
   now opens its scope on its own route, which nests on the same route and refuses on another.

Sabotage, then coverage: 31 mutants over the spec, the hooks, the port and the collection; 28
killed on the first pass. The three survivors were each untested rather than equivalent: the
read-only view over `metadata` (nothing needed it — deleted, `86b8b9f01`), a port resolved
lazily under a binding without a transaction, and the unguarded command port, which only matters
for a read resolved inside another read (both pinned, `979597e9a`). A 31st-plus mutant building
the entry outside the policy's `try` also died. Patch coverage 100% of added lines (296/296), and
100% of the new modules' branches, over the unit and Postgres legs together.

Residue I would still distrust: an audited operation nested inside another operation's
transaction writes its failed or denied row into that transaction, and loses it if the outer
one rolls back; a flood of denied calls is a flood of audit writes (rate limiting is not this
plane's); the Postgres leg wires the collection without tenancy. Two entries above cite evidence
that no longer resolves and are superseded by the corrected entries after them — the checker
reports them, and append-only keeps them.

## Self-audit — P2, 2026-09-28

Scope: the branch against `main`, 2 commits and 9 files, about 700 lines: the invariant, the kit
arm, two batteries, two docs pages, the changelog and this log. I re-read §6 and §12 and rows 9,
10 and 17 first. Both P2 deliverables exist, and §6's DST leg has its retry leg.

**The retry leg first ran with no retries, and only the non-vacuity check caught it.** The mock's
resilience executor passes through by default (`src/forze_mock/execution/module.py:346`). So the
operation-level retry wrap retried nothing, and the bound run was green over a sweep where no
attempt was ever retried. The leg now runs the mock's real executor and counts the executor's
`retry_attempt` events. A sweep with none fails the test. The last run had 41 retries and 26
rolled-back attempts that had written their row, and every committed edit carried exactly one row.

**What the invariant reads, and why it is stated for fail-closed actions only.** The trace
records a port call when it starts, not when it returns (`record` is only called before the
inner call, and a return is recorded only under value capture). So a failed audit write that
an `on_failure="ignore"` action swallowed still reads as a row. For a fail-closed action that
failure rolls the transaction back, so every call left in a committed transaction completed.
The docstring and the docs state the limit. An `ignore` action is not what "exactly one row"
describes anyway.

Sabotage, then coverage. 13 mutants over the invariant and the arm, all killed. Four of the kills
needed legs that the first battery did not have, and they now read a synthetic history:

- a committed transaction with no effect needs no row;
- a read of the trail is not a row;
- a rolled-back transaction is not judged;
- a run whose trace carries no transaction ids is not judged. That is production's trace, where
  the ids are `None`, and without the guard all its writes would be read as one transaction.

Patch coverage is 100% of added lines in `src/` (48/48).

Residue I would still distrust:

- The invariant is blind to effects written outside a transaction, which is what
  `transactional=False` is for. Those operations are outside what it checks, and that is stated.
- The kit arm assumes the audit deps module's `tx_route` is the kit's own. A mismatch fails at
  the first audited write with the core's nested-scope error, not when the kit is built.

## After the first review round (P2) — 2026-09-28

An independent review and one bot finding reached three defects the self-audit did not.

1. **The kit's dated and lineage reads were audited as writes.** `effective_on`, `timeline`,
   `history` and `as_of` only acquire query ports, but were never marked `QUERY`. So the arm
   gave them a read-write transaction and ignored `audit_reads`: `"never"` still wrote
   `allowed` rows. They are now marked `QUERY` where they are built, which also puts them under
   the read-only guard and lists them as reads, including to an MCP projection of reads.
2. **The invariant skipped effects written outside any transaction.** An operation left out of
   the audit has no transaction unless something else binds one, so the most likely regression
   was never judged. Such a write is now reported, and a simulation contrast (an unaudited,
   untransacted edit) must produce the report.
3. **The unit is the transaction, not the operation.** An audited operation dispatched inside
   another's transaction adds a second row to that transaction, and it reads as a double record.
   Operation trace events carry no transaction id, so attributing a row to an operation is not
   sound under concurrency. The limit is stated rather than guessed around.
