# T-0069 — Session revocation fast path, phase 1

Executing phase 1 of [RFC 0069](../rfcs/0069-session-revocation-fast-path.md) on
`fix/authn-atomic-revocation`. The revocation paths commit atomically. Login's and refresh's
eligibility checks share one transaction with their session inserts, under a locking read of
the policy principal. The mock's `deactivate` revokes sessions.

The plan turned up three load-bearing questions the RFC does not settle (entries 1, 3 and 4).
They went to the author before any code was written, and the author accepted every proposal
below on 2026-10-13.

MEDIUM is a defect in this work and is fixed on the branch; the LOWs are answered in the PR.

The other two MEDIUMs were fixes in place. The changelog now says a custom lifecycle must raise
`RefreshTokenReuseError` or its reuse revocation rolls back. The deps-wired probe gained the
test it lacked: with it removed, every suite stayed green. The LOWs:

- **The password hash runs inside the transaction for change and reset.** This is accepted.
  Both adapters hash between their first read and their first write, and moving the hash out
  would split the adapters. The operations are rare and authenticated or token-gated.
- **A missing transaction manager surfaced on the first request.** Fixed: the manager is
  resolved when the handler is built, so `check_wiring` reports it.
- **Deactivation and a password change for one principal can deadlock.** They take their
  locks in opposite orders. This is reasoned, not reproduced. Postgres aborts one of the
  two, and both stay atomic.
- **Two recipes did not mention the transaction manager.** Fixed. LOGOUT,
  PASSWORD_CHANGED and PRINCIPAL_DEACTIVATED events now fire before commit. Those events
  are best-effort observability, and the adapters hold no context to defer them.
- **Races outside this phase.** A login that verified the old password can commit after a
  password change's revocation. An API key can be issued while its principal is
  deactivated. Neither is introduced here or claimed by the RFC; both belong to the phase 2b
  census.

```divergence
evidence: src/forze_postgres/kernel/gateways/write.py:1436-1441 — `missing = expected_ids - updated_ids` raises `exc.concurrency("Failed to update records")`; tests/integration/test_forze_authn/test_pg_revocation_transactions.py — the logout-racing-a-refresh test failed with that error before the fix
action: decided
proposal: ASSUMED — `revoke_sessions_matching` rereads and rebuilds a batch that went stale, up to three times in a row, then raises. The reread drops the rotated session and revokes the one that replaced it.
```

The review's other findings were answered in their threads:
- **Refuted: dropping expired sessions from the filter.** The verifier does not check a
  session's `expires_at`, and an access token's lifetime is configured apart from the
  session's, so an expired session can still back a valid access token.
- **Out of scope: lifecycle events firing before commit.** Deferring every event would drop
  `REFRESH_REUSE_DETECTED`, which is emitted in the transaction that rolls back.
- **Out of scope: password verification inside the transaction.** Moving it out would split
  the password lifecycle port.
