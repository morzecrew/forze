```divergence

claim: §5's matrix says the process tier is rlimits plus a workspace plus an optional uid drop and never says how the limits are applied; `preexec_fn` is the only in-process route and CPython documents it as unsafe in a multithreaded program, which this worker is — the production runtime binds a ThreadPoolCpuExecutor
evidence: src/forze/base/primitives/cpu.py:14 — an ExecutionRuntime scope binds a bounded thread pool it owns, so the fork happens with other threads live
action: decided
proposal: ASSUMED — the limits are applied by a re-exec shim rather than a fork-time callback: the child is spawned as the interpreter running a bootstrap that calls `setrlimit` and then `os.execv`s the request's own argv. No callback runs between fork and exec, the limits are in force before the target image loads, and it works for any argv rather than only for interpreters. The cost is recorded rather than hidden: a missing or non-executable program now fails inside the shim instead of at the spawn, so `spawn_failed` is detected from the shim's own exit rather than from `create_subprocess_exec` raising, and owes its own test.
```
