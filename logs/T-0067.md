## Self-audit — 2026-09-17

Scope: the whole branch against `main`, 2 commits, 11 files (+864 −1): `period.py` (192 lines),
the oracle's `no_overlapping_periods` (106), two batteries (456), docs, changelog, the vulture
baseline, this log. Spec re-read first (RFC 0067 §5.1, §5.3, §6, §11).

**Finding 1 — the oracle raised on a `key` it could not group. Fixed (`1c20e1a33`).**
`by_group[fields[key]]` goes through `defaultdict.__getitem__`, so an unhashable owner value —
a dict recorded by mistake — raised `TypeError` from inside the invariant and ended the run's
checking. Reported as a malformed marker now, like every other thing a marker can get wrong.
Verified red against `e3917a187`.

**Finding 2 — the oracle raised on markers that mixed grains for one owner. Fixed
(`1c20e1a33`).** Each marker built a valid `Period`, so the mismatch survived construction and
surfaced in `entries.sort(key=…start)`: `TypeError: '<' not supported between instances of
'datetime.datetime' and 'datetime.date'`. The group key now carries the grain, the mixture is
reported once per owner, and each grain is still swept — so an overlap inside one grain is not
lost to the other's noise. Verified red against `e3917a187`.

Both are the same defect class and the same blind spot: the invariant's own docstring promised
that a bad marker is *reported rather than raised*, and the first draft honoured that promise
only for the two cases it had thought of.

**Finding 3 — a surviving mutant, and the test gap behind it. Fixed.** Thirteen sabotages, one
survivor: swapping the two open-end branches of `_reaches_further` left all 81 tests passing.
The why is the finding — the existing open-ended leg put the open period *first*, where it is
adopted by the `covering is None` path and the branch is never consulted. Two legs added: an
open-ended period reached second must keep covering later ones, and a closed period must not
displace an open one that is already covering. Both verified red under that exact mutation.

**Sabotage sweep: 13 mutations, 12 killed immediately, 1 survivor fixed above.** The killed set
covers both closed-bounds sets, `overlaps`' two directions and its shared-endpoint rule, the
empty guard, both construction refusals, both `contains` helpers, the covering choice, the
missing-field check, the grain partition and the grain report.

**Patch coverage: 56/56 lines in `period.py`, 43/43 in the oracle** — every added line executed
(`audit_scope.py patch-coverage --base main`). No uncovered detection branch.

**Residue, then fixed on request (`fffec7b45`).** Seven `tests/unit/test_forze_dst` tests
(`test_sweep.py::TestParallelMatchesSequential`, `test_distributed_prove.py::TestFlagshipFuzz`)
failed **under `--cov`** and passed without it, identically on `main`, so the audit recorded them
as predating this branch. Asked to fix them here, the "coverage flake" turned out to be a real
defect in `parallel_sweep`:

```
$ uv run pytest …TestParallelMatchesSequential --cov=forze_dst.artifacts --cov-report=
_pickle.PicklingError: Can't pickle <class 'concurrent.futures.process._CallItem'>:
it's not the same object as concurrent.futures.process._CallItem
```

`ProcessPoolExecutor` wraps each task in a private stdlib class and pickles *that* by name; under a
pytest-cov session whose source is an importable module inside `forze_dst`, the parent's
queue-feeder thread stops resolving the name to the same object. Bisected: a path source
(`--cov=src/forze_dst`) passes, a package name (`--cov=forze_dst`) passes, any module inside it
(`forze_dst.artifacts`, `forze_dst.oracle`, `forze_dst.oracle.invariants`) fails; a plain
`coverage run --source=forze_dst.artifacts` does **not** reproduce it, and `spawn` does not avoid
it because the failure is in the parent. Module identity is intact in the main thread immediately
before the pool runs and afterwards, so the mismatch is transient inside that thread — the
mechanism below pytest-cov is not pinned here, and the fix does not depend on it.

`multiprocessing.Pool` pickles the caller's `run` and the seeds and nothing private, which the
function's contract already required. Ordering, chunking and the worker default are unchanged.
Pinned by a pytest subprocess in the configuration that fails, because nothing smaller reproduces
it, and verified red against the executor.

**This mattered beyond the suite:** an application running its own DST sweep under `pytest --cov`
in CI would have hit the same failure, which is what turned "coverage flake, not mine" into a
user-facing fix.

Not audited: how RFC 0053's kit will consume `contains`/`intersects` — they have no caller in
`src/` yet, which is why they sit in the vulture baseline rather than being exercised there.

## Self-audit round 2 — the fixes

**Finding 4 — the oracle reported its violations in hash order. Fixed (`d6b8d805e`).** Round 1's
mixed-grain fix grouped by `(owner, grain)` and then iterated a **set comprehension** of owners to
find the mixtures, so the order of the returned violations changed with `PYTHONHASHSEED`:

```
$ for seed in 0 1 12345; do PYTHONHASHSEED=$seed uv run python -c "…five owners, each mixed…"; done
["'cat'", "'dan'", "'bob'", "'ann'", "'eve'"]
["'bob'", "'dan'", "'cat'", "'eve'", "'ann'"]
["'ann'", "'dan'", "'bob'", "'cat'", "'eve'"]
```

A determinism tool whose report differs between two runs of one seed is not one — and a minimized
counterexample's report is exactly what a reader compares across runs. Grouping is owner-then-grain
in plain dicts now, so insertion order *is* report order, pinned by a subprocess test across four
hash seeds in the shape the idempotency payload-hash test already uses. Single-process tests cannot
see this class of defect: within one interpreter the order is stable, just arbitrary.

**Process note, worth more than the finding.** The sabotage that killed the set comprehension was
run while the fix for it was still uncommitted, so `git checkout --` restoring the mutation also
wiped the fix — and the next run of the suite failed for a reason that had nothing to do with the
mutation. Reconstructed and committed before continuing. The rule exists for exactly this and it
was mine to follow.

## Review round 1 — five findings, all valid

Nine threads from four bots, deduplicated into five findings. Every one reproduced before it was
fixed.

**F1 — `Period` accepted endpoints its annotations only promised** (codeant ×2, greptile P1,
coderabbit). `Period(start=1, end=2)` passes: ints are the same type as each other and order
fine, so the oracle *swept an int marker as valid* rather than reporting it — the quiet half of
the failure mode. A `bounds` string outside the four was accepted too, silently changing overlap
results. Both refused at construction now.

**F2 — a naive `datetime` against an aware one** (coderabbit, Major). One type to a checker and
a `TypeError` to `<`:

```
$ uv run python -c "…Period(start=datetime(2026,1,1), end=datetime(2026,1,2,tzinfo=UTC))…"
mixed awareness refused: TypeError          # a raw TypeError, not a CoreException
CRASH: TypeError can't compare offset-naive and offset-aware datetimes   # two markers, one owner
```

The **third** shape of the crash this invariant's docstring promises not to have — after the
unhashable key and the `date`/`datetime` mixture, both found in the audit. The lesson the first
two did not teach me: the grouping key was `type(...)`, and *type equality is not
comparability*. It is `grain_of()` now — the type plus, for a `datetime`, whether it is aware —
which is exported because the oracle and the value object must agree on it.

**F3 — only one overlapping pair per period was reported** (greptile P1, coderabbit). For
`[1,10]`, `[2,8]`, `[3,4]` the sweep reported the outer against each inner and never the two
inners against each other: two violations where three pairs overlap, so a consumer correcting
what it was handed would leave an overlap behind. The sweep keeps every period still reaching
past the candidate's start and compares each — linear while nothing overlaps, quadratic only in
genuinely conflicting rows.

**F4 — the documented report order was an over-claim** (greptile P2). The docstring promised
recorded-marker order; the code grouped by owner and sorted by start, so with owners interleaved
a conflict completed later could be reported first. Violations are sorted by the marker that
completes them now, which makes the sentence true rather than narrowing it.

**F5 — exported from the facade but not from `forze_dst.oracle`** (codeant, Major), where
`mutual_exclusion` and its siblings are. One line each; my own pass 4 (discipline drift against
the surroundings) should have caught it.

**Sabotage: six mutations over the new guards, five killed, one survivor.** Removing the final
sort passed, because my order leg interleaved the owners but let the first-appearing owner's
conflict complete first too — grouping order and marker order agreed, so the leg did not
distinguish them. Rewritten so the second owner's overlap completes first, and verified red.

**Injection notices:** three `agent-directed-block` notices — CodeAnt's "Use CodeAnt Skill" /
"Fix in IDE" prompt links and CodeRabbit's "Prompt for AI Agents" block. Benign, read as claims,
not acted on, not mentioned on the PR.
