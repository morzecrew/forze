Executing RFC 0024 phase P1 against branch `feat/outbound-oauth-acquisition`.

**Drift count: 0.**

Written before each action, never revised afterwards to agree with what was later settled,
and never folded back into the RFC's own text. The rows proposed below are put forward for

## Readiness: the gate trips, and D-7 is contradicted

The plan is three seams (a pure `build_authorize_url` in `forze_identity/oauth`, an
`OAuth2TokenClient` in `forze_kits/integrations/secrets`, and a `complete_authorization`
handoff), which §2 places over `forze_http` and D-7 requires to be a **declared service**
so the `egress_sensitive` marker applies. Reading `forze_http` against that requirement
turns up three facts, each of which alone stops P1 as specified:

- the service adapter sends a **JSON** body and has no form encoding, while RFC 6749 §4.1.3
  requires `application/x-www-form-urlencoded` at a token endpoint;
- `HttpServicePort.invoke` takes no per-call headers and `HttpAuthConfig.kind` has no
  `basic`, so §2's `token_auth="basic"` has nowhere to go on a declared service, and the
  call-time credential path that does exist is keyed by **tenant** while an OAuth client
  secret is per-provider;
- a 4xx response body is discarded by the error mapper, so `invalid_grant` (RFC 6749 §5.2,
  a 400 with a JSON body) cannot be told from a transient 400 — and that distinction is the
  one `CredentialExchangerPort` declares load-bearing, because reporting transient as
  permanent destroys a working credential.

Each is a `LOCKED` contradiction rather than a gap to fill: honouring D-7 requires changing
a core contract (`HttpOperationSpec`) and an integration package (`forze_http`), which is
outside the layering D-3 states and outside what §2 assumed. **Halted.** Two smaller
findings are recorded below because they survive whatever the author decides.

context-free port reaches a context, and what happens when a provider omits the new
refresh token), two are narrowings forced by what the transport can and cannot tell apart,

load-bearing question the RFC left open.

## Self-audit — P1, 2026-09-13

Scope: the branch against `main` at `d439dd3d5` — one commit, 12 files, +2100 / −3, across
source (4), tests (5), docs and logs (3). The RFC re-read first, against §5's checklist,
§8's battery and §9's phase list.

**Seventeen sabotage mutations, no survivors.** The ones worth naming are the two that
would destroy credentials rather than merely fail: treating every rejection as permanent
(7 tests fail) and treating none as permanent (4 fail) — the asymmetry the exchanger port
spells out is measured in both directions, and `invalid_client` joining the permanent set
fails on its own. Dropping the carried-forward refresh token fails 2. Sending the client
secret in the body under `basic`, or never resolving it under `post`, each fail. Skipping
the store write in the handoff fails 12. Removing the state comparison fails 5, and
accepting an absent session state — the replay case — fails 2. Letting an extra parameter
override `redirect_uri` fails 6. Encoding scopes with `+` instead of `%20` fails 1.
Emptying the battery tuple fails its own guard rather than collecting nothing.

The in-process leg was sabotaged too: dropping the error detail from its scripted refusal
fails the classification check, so that leg exercises the mapping rather than passing on
a fake that says nothing.

**Findings — four, all fixed.**

1. **The RFC's battery item 2 was not implemented.** "Exchange succeeds, `put` fails →
   raises loudly, nothing half-stored, a fresh code succeeds" is in §9's P1 list and was
   missing from the battery, which only ever exercised a store that worked. Fixed with a
   proxy store carrying a switch, so the check runs against the same engine as every other
   check and differs only in the one write it is about — and it finishes by proving
   re-consent recovers, which is the whole reason this window is mild.
2. **The URL was never asserted clean.** §5 says the secret must never appear in a URL,
   and the battery checked the body and the reprs only. The httpx leg now asserts that
   neither the secret nor the code is in the request URL — a query string reaches every
   proxy log between here and the provider.
3. **Nothing held the context-factory contract.** A client outlives any one runtime scope,
   so a cached context would leave it exchanging through a dead one. A counting factory now
   pins that the factory is called per exchange.
4. **A malformed success was untested.** A 200 whose body is not a token response is a
   provider or proxy bug and must not burn a grant; asserted now, since the same code path
   decides both.

**Residue.**

- *Both legs share one provider brain*, deliberately — a divergence between them is a
  transport difference rather than two fakes disagreeing. What that cannot catch is a
  provider behaving unlike `ScriptedProvider`; only a real counterparty would.
- *The in-process leg synthesizes the transport's error-detail contract.* That the real
  transport attaches it is the httpx leg's job, and it does; the mock leg states the shape
  the client is written against.
- *No DST leg.* §9 puts battery 7 — a dispatch under forced schedules — in P3, and nothing
  here is scheduling-sensitive beyond the store, which has its own.
- *The egress marker is asserted on a config the test builds*, not on one an application
  wired. A kit cannot reach `forze_http`, so this is as close as the enforcement gets
  until the P2 recipe ships an example whose wiring a test can read.
