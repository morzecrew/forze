# T-0048 · Derived read fields

Executing RFC 0048 against branch `feat/derived-read-fields`.

**Drift count: 0.**

Where building this disagreed with the design for it, written at the moment it
happened. Nothing here is revised afterwards to agree with what was later
settled, and nothing here has been folded back into the RFC's own text. The rows
proposed below are put forward for the author to accept or refuse; execution does
not write them into a decision table itself.

| Class | Test | Meaning |
|---|---|---|

## Audit findings — 2026-09-10

**A-1 · The nullable-key check conflated "has a default" with "may be None".**
The first cut used `FieldInfo.is_required()`, which is false for `note: str = ""` — a
defaulted, non-nullable field and a perfectly good join key. It was refused. Caught by
the itself-derived guardrail's own test, which happens to use that field, so the defect
surfaced as a wrong error message on an unrelated case rather than as a missing refusal.
Fixed with `_admits_none`, which reads the annotation. The lesson is the reusable half: a
guard about *nullability* must read the annotation, never the default, and the two are
one method call apart.

**A-2 · Two behaviours were claimed in a docstring and proven by nothing.** The sabotage
sweep survived both: the factory's cross-tenant refusal, and the routing of a derived read
through the active transaction's view. The second is the sharper miss — the docstring says
"a source row joined outside the overlay would let a snapshot transaction observe a sibling
write it must not see", which is a specific claim about isolation with no test behind it.
Both now have one, and both sabotages are killed.

**Sweep: 13 mutations, 13 killed.** Two of the original twelve were invalid and were
redone — one whose anchor no longer matched after formatting, and one that raised at import
rather than changing behaviour, which would have counted as a kill for the wrong reason.

**A-3 · The derived field was settable on a create command and nothing refused it.**
`materialized` carries exactly this rule — a value the backend produces is not one a
caller sets — and the derived declaration did not. A create command could name the joined
field, and no write path could store it. Found by asking what the *write* side does with a
declaration that only ever describes reads, which the sabotage sweep would not have
reached because no test named the shape. Refused now, with the sibling's wording.

**A-4 · §5.3's divergence bound was argued and not measured.** The design's real risk is
two implementations of one read — a view and a hand-rolled join — and the RFC bounds it by
saying the differential covers it. There was no differential. There is now
(`tests/integration/test_forze_postgres/test_pg_document_derived_read_fields.py`): two
tables and a real view, read through the Postgres gateway and through the mock with the
same spec, asserted equal. The second case records the one place they *do* differ — an
inner-join view omits a row whose source is gone where the mock refuses the read — so the
agreement is not read as total.

**A-5 · Residue.** A first cut of that integration test carried an `if False else None`
expression left over from an edit, which ran green and asserted nothing about the case it
named. Removed, and the test now performs the delete and asserts both failures. Worth
recording because it passed: a test whose subject is a divergence is exactly the test that
can pass while measuring nothing.

**Sweep, round two: 17 mutations, 17 killed.** The four new ones cover the settable-command
refusal, the nullable-key refusal, `_admits_none` reading the annotation rather than the
default, and the malformed-key guard.

## §10(b) answered against the origin application — 2026-09-11

```divergence
proposal: LOCKED as built for P1, and a new phase before the reach the RFC's motivation claims. `DerivedReadField.field: str` becomes a projected field SET producing a nested object, which is what the six `*_json(...)` view helpers already build. Until then P1 unblocks the scalar case only, and the motivation's "14 of 25 aggregates" is not what P1 delivers.
```

**What the schema says, in numbers.** Across the 15 repeatable view migrations:

| Projection shape | Count | Served by P1 |
|---|---|---|
| scalar one-hop (`c.code AS catalog_code`) | 13 | **yes** |
| nested reference object (`entity_json(c) AS catalog`) | 27 | no |
| arithmetic / `COALESCE` aggregate / `CASE` | ~79 | no, and no declaration would |

The 27 nested fields are all `ReadEntityReference` — `id`, `rev`, `name`, `number_id` — built by
`public.entity_json` and five siblings that project wider subsets (`detail_json` adds five
fields, `status_aware_json` adds `status`, `logical_slot_json` is a different shape
entirely). **Twelve are required**, and a required field is exactly what makes the mock
refuse the row.

Of the four fields the origin report named, `catalog_code` is the scalar and `supplier`,
`order` and `group` are all nested objects.
