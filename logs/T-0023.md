## What "reuses the projection `forze_mcp` already runs" can mean here

D-1 is `LOCKED` and says the bridge reuses the operation-to-schema projection that
`forze_mcp` and OpenAPI already run. A literal shared function is forbidden:
`forze_mcp` is an import-protected module whose only sanctioned importer is `forze_cli`,
so `forze_kits` cannot import it. The reuse that is available is the one the descriptor
was built for, and its own module docstring says so in as many words.

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-12T18:55:00Z
attempt: 1
claim: D-1's "reuses the operation→schema projection forze_mcp/OpenAPI already run" cannot mean a shared import — forze_mcp is import-protected with allowed_importers = ["forze_cli"], so forze_kits importing it fails the layering contract. The reuse available is the shared source of truth: OperationDescriptor, which exists so that "a driving adapter (MCP, an auto-generated HTTP router, …) can build a tool/route catalog without re-deriving schemas"
evidence: src/forze/application/execution/operations/descriptors.py:6
action: decided
proposal: ASSUMED — the bridge reuses the descriptor (input_type/description/sensitive) and the plan-derived OperationCatalogEntry, not any transport package's code. No decision row needs to change; this records the reading so a reviewer does not read the absent import as a missed reuse.
```

## A sensitive operation named in the allowlist is refused, not skipped

The RFC settles this itself: §3 says such operations are excluded "exactly as they are from
route/MCP generation", and both of those surfaces raise rather than drop, on purpose and
before adding any tool.

## §3 returns a tuple, §4 needs a toolset, and the difference is a security property

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-09-12T19:20:00Z
attempt: 1
claim: §3 declares `operation_tools(...) -> tuple[ToolDef, ...]` while §4 takes `tools: OperationToolset  # the projection + its operation bindings`, and the two cannot both be the whole story — a bare tuple of ToolDefs carries no binding from tool name back to operation key, so a dispatch given only the registry would resolve any name in the catalog and D-5's mandatory allowlist would stop being enforced at the moment it matters, on the agent's actual call
evidence: rfcs/0023-operation-tool-bridge.md:59
action: decided
proposal: ASSUMED — `operation_tools` returns an `OperationToolset` that carries the bindings and exposes `.defs` as the `tuple[ToolDef, ...]` §3 promises, so the app still hands its SDK a tuple. Dispatch resolves the tool name against the toolset only: a name outside the palette is a ToolResult(is_error=True), never a catalog lookup. The allowlist is then a property of the dispatch path, not only of the projection.
```

## Self-audit — 2026-09-12

Scope: the whole branch against merge base `b3410582b` — 3 commits, 5 source files
(+421), 4 test files (+736), 3 docs files (+256), 1 config line. Everything the branch
touched. Re-read RFC 0023 §§1–9 before reading the diff.

**Four findings, all fixed on the branch.** Ranked by what they would have cost.

**1. A server-side failure was absorbed into the agent's turn.** `dispatch_tool_use`
caught every `CoreException` and answered with `ToolResult(is_error=True)`, including the
500-class kinds. `error_envelope` masks those to a generic detail, so the model received
"an internal error occurred" with nothing to act on, the application loop saw a *handled*
tool call, and nothing was logged anywhere — an internal bug would disappear into a
conversation. D-3 is explicit that infrastructure failures propagate. Fixed: a
`server_error` envelope re-raises, carrying its traceback to the app's own handling.
Reproduced red first (`DID NOT RAISE`), and the sabotage that removes the re-raise kills
its test.

**2. A result the descriptor does not describe was handed to the model as a Python
repr.** `_content` fell through to `str(result)`, so a handler returning anything that is
not a `BaseModel` — a mapping, a list, a raw attrs `Page` — reached the agent as
`Page(hits=[...], page=1)`, which a model cannot parse and will confidently invent fields
around. §4 says the content is JSON-projected. Fixed: JSON projection under a `result`
key, a `str` passed through, and a value that is not JSON at all refused as a wiring
defect rather than stringified. *Worth recording why this was nearly missed:* the tenancy
test asserted `"a-only" in str(own.content)`, which passes on a repr as readily as on a
dict. The probe that settled it printed the real content type — the kits document `list`
returns a pydantic `Paginated`, so the production path was never affected, but the
fallback branch was wrong and untested.

**3. A test that passed by coincidence.** `test_the_palette_keeps_the_allowlists_order`
used `["calc.void", "calc.double"]`, whose order happens to equal reverse-alphabetical —
so an implementation that sorted the selection satisfied it. The sabotage
(`sorted(include, key=str, reverse=True)`) survived, and the *why* was the fixture, not a
second guard. Now parametrized over both directions, which no fixed ordering can satisfy;
both sabotage directions kill it.

**4. Two over-claims in the docs page.** It said a tool's description is "its operation's
docstring" (it is the descriptor's `description` field, which an app sets) and that the
palette "is wired at startup" (nothing enforces when it is built). Corrected to what the
code does. A third over-claim was introduced *by* the correction — "the same text the HTTP
and MCP surfaces show", when MCP appends its own auth and deadline sentences — and was
caught re-auditing the fix, which is the pass the first two would have escaped.

**Sabotage: 14 mutations, 13 killed immediately.** The palette bypass (resolve a name
from the registry instead of the toolset), the read-only filter, the sensitive refusal,
the empty-allowlist refusal, input validation, the error sanitization, the dedupe, the
void-result shape, the echoed `tool_use_id`, the description passthrough, the schema
source, and replacing the caller's context with a fresh one — that last one kills three
tests, which is what proves the tenancy test is not vacuous. The single survivor is
finding 3.

**Coverage after sabotage: 125/125 added source lines, 100% branch,** measured over the
kits-integration and MCP suites together. No uncovered detection branch.

**Suites run:** `tests/unit/test_forze_kits` + `tests/unit/test_forze_mcp` — 1316 passed
before the audit fixes; the new files 34 passed, then 308 passed across both directories
with coverage after them. `just quality` green on all 19 gates, including this branch's
own docs-snippet gate over the new page.

**Residue — what I would still distrust.**

- *Battery 6 has no real-backend leg*, by the reading logged above. If the author wants
  it, it is additive.
- *A missing bound tenant reaches the model as an actionable error.* It is a 4xx kind by
  the repo's egress classification, so the bridge reports it to the agent, which can only
  retry it forever; the wiring, not the model, is at fault. Reclassifying it here would
  mean disagreeing with the classification every other surface uses, so it stands.
- *`OperationToolset.bindings` is a plain mapping on a frozen class*, so in-process code
  could mutate the palette after projection. Left alone: anyone who can do that can call
  `run_operation` directly, so it defends nothing.
- *The three test files each define their own `_In`/`_Out`/`_Doubler`.* Deliberately not
  extracted — the shapes are trivial, and the parity test needs to mirror the MCP test's
  fixture rather than share one with the dispatch suite.
