# T-0065 — Snapshot-consistent export and its verification

Planning [RFC 0065](../rfcs/0065-snapshot-consistent-export-verification.md) P1, the phase §12
calls independent and useful alone: `server_version` in the manifest, the import major-version
gate, and batteries. **Stopped at the readiness gate before any code.** P1 needs three decisions
the spec does not settle. Each comes from carrying the origin's `pg_dump` / `pg_restore` shape
onto a plane that reads through backend-agnostic ports.

## Plan

- `forze_kits/integrations/portability/manifest.py`: `Manifest.server_version`, recorded at every
  level (D-8's third question, the RFC's own leaning: diagnostic there, and cheap).
- `export.py`: learn the server version while exporting and write it into the manifest.
- `import_.py`: refuse when the client's major version is older than the recorded server's major
  version (§5.3, D-4). `forze_version` stays diagnostic.
- Batteries per §6: an older client major refuses, an equal or newer one imports, and a differing
  `forze_version` does not refuse.

## Decisions the spec does not settle

Three are load-bearing, so this stops at the readiness gate for the author.

1. **Where the version comes from.** The plane reads through ports on the execution context:
   documents, storage, graph and counters (`src/forze_kits/integrations/portability/export.py:379`,
   `:419`, `:485`, `:572`). No port reports a server version, and §4's scope says "no new port".
   The plane cannot ask Postgres its version without a new port, a capability on an existing one,
   or an import from `forze_postgres`, which the kit layer does not do.
2. **Whose version, when an archive spans several backends.** One archive routinely carries
   documents from Postgres, counters from Redis and blobs from S3. A single `server_version`
   field names one of them. A per-route map is a different field, and it is a different gate
   too, since each route would compare against its own target.
3. **What "the client" is on import.** In the origin, the client is `pg_restore` reading a dump
   format that the server version shapes. Here, import decodes JSONL rows through the target
   application's own create models and writes them through its ports
   (`src/forze_kits/integrations/portability/import_.py:292-310`). Nothing on the import side
   decodes a server's wire types, so "an older client silently mis-decodes a type it does not
   know" has no reader to happen in. The version pair that exists at import is the exporting
   backend's and the target backend's. Whether *that* comparison is the gate, and in which
   direction it refuses, is a decision §5.3 did not make.

P2 (the `snapshot` level) has its own open questions, listed in D-8. It also has to answer how an
export spanning a non-Postgres route (counters, blobs) meets D-3's single-client refusal. It was
not planned here.

**Drift count: 0**

## Correction — 2026-09-29

Item 3 above says the version pair that exists at import is the exporting backend's and the
target backend's. Neither exists today. No port reports a version (item 1), so an export
records none, and an import cannot read the target's. It is the pair a gate *could* compare once
item 1 is settled, which leaves item 3's question in place: whether that pair is the gate, and
which direction refuses.
