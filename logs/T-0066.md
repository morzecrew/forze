## Gaps the RFC does not list

§5.3 says each adapter declares what it can enforce "in the shape its plane already uses", and
that shape does not exist: the nine capability declarations are module-level constants consulted
*inside* each renderer, never exposed on a port. The declared half therefore needs a new
port-visible surface, which is the first entry below. The second is where enforcement attaches in
the mock. A third observation needs no entry because the scope answers it: D-5 (`LOCKED`) requires
a parity battery comparing mock and backend, which P1 alone cannot have — §12 puts the backends in
P2, so executing P1 and P2 together is what satisfies it, and P1 in isolation would have shipped
the optimistic-oracle risk §5.5 names.

## Self-audit — 2026-09-18

Scope: 8 commits, 29 files, ~1900 lines (`audit_scope.py scope --base main`). Ten passes walked;
what they turned up, and what remains.

**Fixed during the audit**

1. **`skip_null` was untested and the class name said otherwise.** The legs used `label=""`, an
   empty string, so a sabotage applying `skip_null` unconditionally passed the whole class. Both
   directions now run against a nullable field, plus the partly-null tuple that distinguishes
   `any` from `all` — the second surviving mutation. (`819f645b6`)
2. **No DST leg, which §6 requires.** Added, with the ungoverned contrast §6 asks for: the same
   racing workload against the same spec minus the guarantee must produce two current rows, or
   the governed run is green because nothing collided. (`c70d14107`)
3. **The mock's unenforced-member arm was unreachable and unproven.** Reached by declaring a
   capability the store does not implement; it refuses the write rather than storing the row.
4. **Two validators' skip branches were dead.** The `isinstance` filter is what makes the P3
   transition safe, and nothing exercised it. Covered by driving the hook directly.
5. **My first census of the mock's write paths missed five of nine.** `grep 'store\['` found four;
   `self._store()[pk] = ` forms hid the rest — `touch`, `delete` ×2, `restore` ×2. All nine route
   through `_write_row` now, proven by a grep showing one direct assignment left, the helper's own.

**Evidence**

- 14682 passed / 7 skipped; `just quality` 19/19.
- Patch coverage **99.49%** (197/198) with the integration suites in the profile. Unit-only
  reported 84.85%, which is the misleading number §9 warns about — every uncovered line was in
  the Postgres files the unit run never executes.
- 11 sabotages, each killed by exactly the legs that should kill it: 5 on the mock (enforcement
  removed, self-exclusion dropped, filter ignored, `skip_null` unconditional, `any`→`all`),
  3 on Postgres (never refuses, filtered-as-unfiltered, partial-index query inverted), 3 on Mongo
  (never refuses, sparse not counted, partiality ignored). One earlier survivor was finding 1.

**Residue**

- `partial_unique_index_exists`' empty-columns guard is unreachable (construction refuses an empty
  `fields`) and kept for symmetry with the sibling beside it. The one uncovered added line.
- **Neither validator compares what an index's predicate *says*** against the guarantee's `where`.
  That is deciding whether two boolean expressions agree, which is the database's job — so a
  partial unique index whose predicate disagrees with the declaration passes validation and then
  refuses rows the guarantee meant to allow. Stated in both docstrings and in the docs.
- **No Mongo parity leg.** §6 names Postgres for parity and that exists; the mock-versus-Mongo
  comparison does not.
- **`ExclusionViolation` maps to `precondition`, not `conflict`** (`forze_postgres/kernel/client/errors.py:114`).
  P3 maps `NonOverlapping` to an exclusion constraint, so Postgres would refuse with a different
  kind than the in-memory store's `conflict` — a parity break waiting for P3, found here and not
  fixed here because nothing maps that member yet.

## Review round 1 — 2026-09-18

Five reviewers read the branch. Four findings were the same one seen from different angles, and
two forced a decision the RFC had not settled.

```divergence
decision: unlisted

class: discovery
at: 2026-09-18T19:40:00Z
attempt: 1
claim: Mongo has no mechanism for `skip_null`; sparse indexes do something else, so declaring the capability would reconcile and not enforce
evidence: src/forze_mongo/adapters/document.py:56-72
action: decided
proposal: ASSUMED — a backend maps only the axes it has a mechanism for; `skip_null` is Postgres-only until Mongo grows one
```

The adapter claimed `unique_together_skip_null` on the strength of sparse indexes. A sparse index
skips a document only when *every* indexed field is missing and still indexes an explicit null, so
it exempts neither a tuple holding a null nor a compound tuple with one null member; a
`partialFilterExpression` cannot close the gap either, since its admitted operators cannot say "not
null". The claim would have reconciled at wiring and then not enforced — the exact failure the
capability convention exists to prevent, and a break of D-5's parity requirement rather than a
narrowing of it. Reconciliation now refuses the declaration on Mongo.

```divergence
decision: D-9
grade: OPEN
class: spec-gap
at: 2026-09-18T19:55:00Z
attempt: 1
claim: an isolated transaction's guarantee check cannot see a concurrent transaction's rows, so two commit
evidence: src/forze_mock/adapters/_mvcc.py:298-330
action: decided
proposal: ASSUMED — a guarantee is re-checked against the committed store at commit, because a unique index is not snapshot-scoped
```

§5.2 puts enforcement at write time and says nothing about transactions. In the in-memory store a
write inside a transaction is checked against that transaction's own view, which by construction
excludes a concurrent transaction's uncommitted rows — so two transactions inserting different ids
carrying the same guaranteed tuple both passed and both committed. A real unique index is not
snapshot-scoped: the second inserter blocks on the first and then fails. Each buffered write now
re-runs its own check against the committed store at commit, raising `conflict` before the
serialization checks, for the same reason a duplicate id does.

## Review rounds 2 and 3 — 2026-09-18

Five findings, all valid, none contradicting a decision — every one is a place the round-1 work
was right in principle and too coarse in practice.

1. **The guarantee's `where` fields were not validated, only the tuple's.** The worse half of the
   same mistake: a filter over a name no row carries selects nothing, so the uniqueness holds over
   the empty set and every duplicate it was declared to refuse is accepted. A guarantee that never
   fires and never fails. The filter's field roots are checked with the tuple's now.
2. **The commit-time recheck queued every write, not the final value of each key.** A transaction
   that wrote a tuple and then moved the row off it was judged against the tuple it had abandoned,
   so a concurrent committer holding that tuple rejected it although its final overlay did not
   conflict. One entry per key, read from the overlay at commit — which also drops a key deleted
   within the transaction, since nothing lands for it.
3. **Both predicate comparisons were substring tests.** `status` was satisfied by an index filtered
   on `status_code`, and `deleted` by `(deleted_at IS NULL)` or by `(label <> 'deleted')`. Mongo
   walks the filter document now; Postgres strips string literals and matches on identifier
   boundaries. Not a SQL lexer, deliberately: the comparison decides whether the predicate mentions
   the right column at all, and buying exactness on unusual quoted identifiers does not change what
   the check can conclude.
4. The changelog entry broke the house concision rule in `CONTRIBUTING.md`. Trimmed.

**Residue after three rounds**

- Predicate *equivalence* is still not decided, on either backend, and will not be: an index on the
  right column restricted to the wrong value passes. Stated in both docstrings and on the docs page.
- The Postgres identifier match does not decode quoted identifiers with unusual casing. A column
  that can only be named as `"Is Current"` would not match the guarantee's field name; no spec in
  the repository has one, and the failure mode is a refusal at startup rather than an acceptance.
