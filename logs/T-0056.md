# T-0056 — Preview binding

Executing [RFC 0056](../rfcs/0056-preview-binding.md) on `feat/preview-binding` — its one phase: the
wrapper, the mixin, the fingerprint, the check, the battery and the docs section.

## Plan

- `forze_kits/domain/preview/` (new, the RFC's `forze_kits.domain.preview`):
  - `canonical_fingerprint(model, *, exclude)` — the one computation both sides call.
  - `Reviewed[T]` (a `BaseDTO` carrying `data` and `fingerprint`) and `ReviewedCommand` (the
    `fingerprint` field a confirming command carries).
  - `PreviewBinding(name, projector, exclude)` — the single declaration both sides read (D-8's
    leaning): `.reviewed(ctx, args) -> Reviewed[T]` for the preview operation, and
    `.bind(binder)` binding the check. The projector is the app's async function over
    `(ctx, args)` (D-6).
  - The check is a **transaction-scope `wrap`** step (D-3): it recomputes the projection inside
    the operation's transaction, before the handler, and refuses with
    `precondition(preview_changed)` naming the binding, never the values (D-1, D-2). An operation
    without a transaction route is refused when the plan freezes.
- Battery (`tests/unit/test_forze_kits/...`): round trip; a changed included field refuses and
  its write does not happen; a changed excluded field passes; the preview side and the check
  read one declaration; ordering and value stability; cross-process determinism (subprocess ×4,
  the shape the cursor-token path uses); a write landing between preview and submit refuses.
- Docs: a section beside idempotency, leading with "did I already send this?" versus "is this
  still what I saw?"; changelog.

Read before code: §5's rejected alternatives — signing the fingerprint, storing the preview
server-side, comparing `rev`s — each is a shape the implementation will reach for.

## Decisions the spec does not settle

One is load-bearing, and it is put to the maintainer before code:

1. **Whether the fingerprint's byte form is stable enough to be stored** (D-4 `ASSUMED`). D-4
   builds on `stable_payload_fingerprint`, whose own docstring says its byte layout "is not a
   stable wire format across orjson versions/options" and that it is "for cache/dedup
   fingerprints only" (`src/forze/base/primitives/fingerprint.py:74-77`). For an in-flight preview
   that is the safe direction — an upgrade between preview and submit refuses, and §9 accepts
   it. But [RFC 0055](../rfcs/0055-scoped-disclosure.md) stores the fingerprint on a disclosure
   snapshot so that "a recipient can prove what they were shown"
   (`rfcs/0055-scoped-disclosure.md:109-111`), and a digest over bytes a dependency upgrade can
   change silently — without the prefix changing — cannot be recomputed later.

Decidable during execution, each owed an entry before it is taken: D-8 (one `PreviewBinding`
declaration, with the preview helper on it); the step shape in place of §5.2's handler decorator
(operations take behaviour as plan steps, as RFC 0060 row 14 found); the projector's signature and
what the preview and submit arguments share; how a set in the projection is ordered (pydantic's
JSON mode keeps set iteration order, which is hash-seeded); and whether §6's DST leg ships here or
as an interleaving unit leg with the DST scenario deferred.

```divergence
decision: D-4
grade: ASSUMED
class: spec-gap
at: 2026-09-28T18:32:21Z
attempt: 1
claim: D-4 builds on stable_payload_fingerprint, whose byte layout its own docstring disclaims as a wire format across orjson versions; RFC 0055 stores the fingerprint so a recipient can prove what they were shown, which needs it recomputable after any dependency upgrade
evidence: src/forze/base/primitives/fingerprint.py:74-77
action: departed
proposal: ASSUMED (maintainer's answer) — canonical_fingerprint owns its canonical form: the model's JSON-mode dump with every set sorted by its canonical bytes, serialized by the standard library with sorted keys and fixed separators, hashed with SHA-256 under a versioned prefix ("sha256-c1:"). D-4's second half holds: changing the form means a new prefix, so an old fingerprint refuses rather than matching. stable_payload_fingerprint stays what it is, a cache and dedup key.
```

## Self-audit — 2026-09-28

Scope: the branch against `main` — 5 commits (the feature, three test pins, and the docs and log
below), ~1k lines: the `forze_kits.domain.preview` module, the unit battery, the DST leg, the docs
page and changelog. Re-read RFC 0056 §5–§7 and §11 first; every §6 leg exists.

Findings, most severe first:

1. **The in-transaction check did not keep the handler on the previewed state** (fixed before the
   first commit, after a halt on D-3 and the maintainer's answer). At read committed, a write
   landing between the check and the handler's own reads reached the handler; the DST sweep at
   16 flows × 4 seeds broke the invariant with the binding in place. The binding now runs its
   operations at snapshot isolation or stronger, and the same sweep holds with both
   confirmations and refusals in it.
2. **The bound DST run was vacuous at its first size** (fixed). At 4 flows every confirmation
   was refused, so "the invariant held" said nothing; the run now asserts both outcomes occur —
   which is what surfaced finding 1 once the sweep grew.
3. **Nothing pinned the canonical form** (fixed, `test_the_form_is_pinned`). A change to how an
   enum, a datetime or a set renders moved every fingerprint with no test failing — the silent
   break the versioned prefix exists to prevent.
4. **"Checked before the handler" was untested** (fixed). A proper after-the-handler mutant
   survived, because a refusal inside the transaction rolls the write back either way; it matters
   when the handler changes what it confirms, now pinned.
5. **The docs overclaimed twice** (fixed): a link sent "per-owner write serialization" to a page
   that never mentions it, and a snapshot conflict was called a `conflict` when it is a retryable
   `concurrency`.

Sabotage, then coverage: 22 mutants over `binding.py` — rendering, exclusion, isolation, the
check's position and presence, declaration refusals — all killed, one (S17) only after the leg in
finding 4 replaced a kill that came from a double handler run. Coverage 100% of lines and
branches after a list field was added (the list branch was untested, and a list's order is
data).

Residue I would still distrust: `exclude` names top-level fields only; the projector runs twice
per confirmation (once for the check, once in the handler if it reads the same rows); an
operation that already declares an isolation level must pass it to `bind`, or the two levels
refuse at freeze — loud, but found only then.
