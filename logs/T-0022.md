## Self-audit — 2026-09-13

Scope: the whole branch against merge base `347ef046a` — 2 commits, 5 source files
(+122/−13), 3 test files (+264), 3 docs files (+84). Re-read RFC 0022 §§1–4 before the
diff.

**One finding, fixed. The rest of the sweep came back clean, with the evidence below.**

**1. The docs line over-claimed the span tag, on the RFC's own flagship path.** It said a
declared route "tags its span", full stop. The gate is universal — every service is
configured through `HttpServiceConfig`, so wiring cannot dodge it — but the tag is set in
the adapter's `invoke`, and §1's recipe hands the underlying *client* to a provider SDK.
Those requests never reach the adapter, so they carry the gate and no tag. Marking them
would mean instrumenting someone else's client. Corrected in the docs and recorded at the
code site, because the next reader of that line will be someone deciding whether the marker
covers their SDK calls.

**Checked and clean, each with what was actually run:**

- *The guard cannot be skipped by the early return.* `__attrs_post_init__` returns early
  for `tenant_aware=True`, which is exactly how a check placed one block lower would apply
  to half the routes. It sits above that return, and the sabotage that moves it below kills
  its test.
- *Only one request site exists.* `grep` over the adapter finds a single
  `client.request` call, so there is no second path that would silently carry no tag.
- *The operation span is real.* The comment claims the attribute lands on the enclosing
  operation span when port spans are off; `_telemetry_factory` opens exactly that span
  (`observability.py:425`), and the third case — nothing instrumented — is covered by a
  test that runs the call with no recording span at all.
- *The inference refusal is byte-identical.* Both configs' messages were compared against
  the pre-change strings, not eyeballed: same sentence, same kind, same default code. A
  test pins the full string literally rather than rebuilding it from the source constant,
  which would have been vacuous.

**Sabotage: 8 mutations, 8 killed.** Disabling the gate, ignoring the acknowledgement,
breaking the default silence, tagging unconditionally, typoing the attribute name, letting
the inference route declare itself insensitive, moving the guard below the early return,
and dropping the RFC-named error code.

**Coverage: 24/24 added source lines, and 10/10 with full branch coverage on the new
module.** Full unit suite 4855 passed. `just quality` 19/19.

**Residue — what I would still distrust.**

- *The `code` on the inference refusals stays `core.configuration`.* Giving them
  `http_egress_unacknowledged` would be wrong (SageMaker is not HTTP) and inventing new
  codes would change what an existing deployment can match on, so the shared helper takes
  the code as a parameter and inference passes none. Their behaviour is therefore
  unchanged, and they remain uncoded.
- *The detail sentence is duplicated across the two inference configs.* Deliberately not
  extracted: one sentence, two call sites, in two packages that share no module — a new
  module to hold a string is the abstraction the repo's own rules refuse. It was already
  duplicated before this change, as a four-line raise.
- *The repo's HTTP codes are dotted (`http.response.validation`) and the RFC names an
  underscored one.* Followed the row verbatim; worth an author's eye if code style matters
  more than the row.
