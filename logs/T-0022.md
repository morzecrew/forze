## Self-audit — 2026-09-13

Scope: the whole branch against merge base `347ef046a` — 2 commits, 5 source files
(+122/−13), 3 test files (+264), 3 docs files (+84). Re-read RFC 0022 §§1–4 before the
diff.

**One finding, fixed. The rest of the sweep came back clean, with the evidence below.**

**1. The docs line over-claimed the span tag, on the RFC's own flagship path.** It said a
declared route "tags its span", full stop. The gate is universal — every service is
configured through `HttpServiceConfig`, so wiring cannot dodge it — but the tag is set in
the adapter's `invoke`, and §1's recipe hands the underlying *client* to a provider SDK.
Those requests never reach the adapter, so they carry the gate and no tag. Marking them
would mean instrumenting someone else's client. Corrected in the docs and recorded at the
code site, because the next reader of that line will be someone deciding whether the marker
covers their SDK calls.

**Checked and clean, each with what was actually run:**

- *The guard cannot be skipped by the early return.* `__attrs_post_init__` returns early
  for `tenant_aware=True`, which is exactly how a check placed one block lower would apply
  to half the routes. It sits above that return, and the sabotage that moves it below kills
  its test.
- *Only one request site exists.* `grep` over the adapter finds a single
  `client.request` call, so there is no second path that would silently carry no tag.
- *The operation span is real.* The comment claims the attribute lands on the enclosing
  operation span when port spans are off; `_telemetry_factory` opens exactly that span
  (`observability.py:425`), and the third case — nothing instrumented — is covered by a
  test that runs the call with no recording span at all.
- *The inference refusal is byte-identical.* Both configs' messages were compared against
  the pre-change strings, not eyeballed: same sentence, same kind, same default code. A
  test pins the full string literally rather than rebuilding it from the source constant,
  which would have been vacuous.

**Sabotage: 8 mutations, 8 killed.** Disabling the gate, ignoring the acknowledgement,
breaking the default silence, tagging unconditionally, typoing the attribute name, letting
the inference route declare itself insensitive, moving the guard below the early return,
and dropping the RFC-named error code.

**Coverage: 24/24 added source lines, and 10/10 with full branch coverage on the new
module.** Full unit suite 4855 passed. `just quality` 19/19.

**Residue — what I would still distrust.**

- *The `code` on the inference refusals stays `core.configuration`.* Giving them
  `http_egress_unacknowledged` would be wrong (SageMaker is not HTTP) and inventing new
  codes would change what an existing deployment can match on, so the shared helper takes
  the code as a parameter and inference passes none. Their behaviour is therefore
  unchanged, and they remain uncoded.
- *The detail sentence is duplicated across the two inference configs.* Deliberately not
  extracted: one sentence, two call sites, in two packages that share no module — a new
  module to hold a string is the abstraction the repo's own rules refuse. It was already
  duplicated before this change, as a four-line raise.
- *The repo's HTTP codes are dotted (`http.response.validation`) and the RFC names an
  underscored one.* Followed the row verbatim; worth an author's eye if code style matters
  more than the row.

## Self-audit round 2 — 2026-09-13

Re-entered after round 1's fix, which is the code most likely to be wrong: it was written
to correct an over-claim and it made a smaller one of its own.

**2. The corrected docs line was still wrong, one level down.** Round 1 said an app that
hands the underlying client to a provider's SDK "keeps the wiring gate but not the
per-call tag". It keeps neither. A bare `HttpClient` is reached through `HttpClientDepKey`
and configured by `HttpConfig`, which is *connection settings* — timeout, redirects, a
response cap — and names no destination at all. There is no `HttpServiceConfig` on that
path, so nothing is declared and nothing is gated.

The useful part of chasing it: this also answers whether the gate is in the right place.
It is, and not by luck — a shared transport has no destination, so "does this hop send
sensitive data out" is not a question it can answer. The governed unit has to be the
service, which is exactly where §1 put the fields. The correction is therefore a
documentation one, not a design finding: say that the gate covers declared services, and
that declaring the hop as a service is what brings it under governance.

**Checked and clean:**

- *The mock is laxer than production here, correctly.* `MockHttpServiceAdapter` takes no
  `HttpServiceConfig` — it is wired from a `MockHttpRegistry` — so a test running against
  the mock is never gated. That is the right asymmetry rather than a parity bug: under the
  mock nothing leaves the process, so there is no egress to acknowledge. The cost is that
  an unacknowledged declaration surfaces when the real adapter is wired, which is a boot
  failure and exactly where the RFC wants it.
- *Nothing else constructs the config.* `grep` across `src/` and `examples/` finds no
  `HttpServiceConfig(` outside its own module, so no in-tree wiring silently acquired a
  new obligation.
- *The route-warning descriptor needed nothing.* It reads only `tenant_aware`.

**Nothing else surfaced.** Round 2 re-walked the ten passes against the same diff: the
fix's blast radius, the mock/simulation parity question, the config's other consumers, and
every prose claim in the diff against the code beside it.

## Self-audit round 3 — 2026-09-13

**No product defects.** Two improvements to the proof, and one check that came back clean
in a way worth recording.

**The comment's claim is now run rather than read.** The code beside the span tag asserts
that the attribute lands on the port's CLIENT span where per-port spans are enabled — the
production shape, and previously believed from a read. A test now wraps the adapter exactly
as the deps layer wraps it (`wrap_port_otel_spans`) and inspects the exported span: the
marker is there, next to `forze.port.surface`. The sabotage that stops setting the marker
kills two tests, and a deliberate no-op mutation leaves all 43 green, which is what makes a
survivor meaningful rather than ambiguous.

**A weak assertion and a blanket ignore, both tightened.** The
"acknowledging without declaring" test asserted only that a flag echoed back; it now states
that constructing at all is the assertion — the gate would raise there if it keyed off the
acknowledgement rather than the declaration. The `_config` helper's `# type: ignore` came
off with a precise parameter type.

**Recorded so it is not read as a regression:** `mypy` over `tests/unit/test_forze_http`
reports errors on this branch, and reported twelve of them before it — `HttpServicePort.invoke`
returns `BaseModel`, so every test in that directory that reads a field off the result is
untyped-loose, including the ones that predate this work. The Types gate is `mypy "src"`,
so tests are deliberately outside it, and the new tests match the idiom of the file they
sit beside rather than inventing a stricter local one.

**Convergence.** Three rounds: one finding, one finding, none. Both findings were prose —
the first over-claimed the span tag's reach, the second was the correction over-claiming in
turn, which is the pass that exists because a fix written under "just correct it" pressure
is the likeliest thing on the branch to be wrong. Ten sabotage mutations across the rounds,
all killed, plus one no-op control.
