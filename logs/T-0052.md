# T-0052 — Versioned facts with correction lineage

Executing [RFC 0052](../rfcs/0052-versioned-facts-correction-lineage.md), P1 + P2 together. P2 was
gated on RFC 0066 P1–P2, which shipped as #444 and #445, so the invariant-only phase has nothing to
wait for. P3 is demand-gated by the RFC's own terms and is out of scope.

A `Correction` is a second aggregate. Its relation, its route and its encryption policy are facts
only the author holds — the same reason `BackendRequirements` describes what to wire instead of
fabricating a `PostgresDocumentConfig`. Requiring it on the policy keeps the kit's rule ("a
correction names its actor and its reason, and both are part of the record") enforceable while the
store stays the author's, and makes the second route visible in the declaration rather than
discovered at resolve.

## Self-audit — 2026-09-19

Whole branch, 4 commits / ~2.6k lines (16 source, 4 test, 3 docs files). Six findings, all fixed.

1. **The kit declared no invariant.** §1 says it declares two storage guarantees *and one
   invariant*, and §9 names `single_current_head` as the detective control for a write path that
   bypassed the handlers. Mine left it to the author, which is a control that silently does not
   exist — nothing about a kit missing it looks different until a second current row appears. The
   kit carries it now, composed with any law the author declared.
2. **Composing `soft_delete` with `versioned` served soft-deleted rows.** Both arms override GET
   and the versioned one binds second, replacing rather than wrapping the soft-delete guard.
   Neither arm's own battery can see it: soft-delete's passes without versioning and versioning's
   passes without soft-delete. The leg lives with the composition.
3. **A vacuous assertion, exposed by writing its contrast.** The invariant legs asserted that an
   op *has a plan* — which every op does. They read the isolation floor the law forces, which is
   what binding one actually changes.
4. **No leg passed filters to a versioned LIST**, so the mapper's conjunction branch — the one a
   real caller takes — was unproven. A sabotage dropping it survived.
5. **The stale-version leg passed for the wrong reason.** By the time a caller's version is stale
   the row is usually superseded, so the not-current check fires first and the version comparison
   is never reached. Disabling it changed nothing. A caller working from a stale cache passes a
   wrong number for a row that is still current, and that is now pinned separately.
6. **Nothing drove an update to a superseded row**, so the mixin's guard — the last line against a
   repair script or a bulk update reaching history — was unproven.

**Evidence**

- 15965 passed / 7 skipped; `just quality` 19/19.
- Patch coverage **100%** (352/352) with the Postgres and Mongo integration suites in the profile.
- 9 sabotages. Five killed on the first sweep; four survived and were findings 4, 5, 6 and the
  composed-GET guard. **Two of the first sweep's "survivors" were no-op mutations** — `ruff format`
  had reflowed the target text, so the `str.replace` matched nothing and the sabotage proved
  nothing. Re-run with an assertion per replacement, one was killed immediately and the other was
  a genuine gap.

**Residue**

- **`UniqueTogether` is frozen-attrs-hashable and carries a dict in `where`**, so `set(...)` of a
  filtered guarantee raises. The guarantee check compares by value, which is what it needs anyway;
  the trap is still in RFC 0066's vocabulary and untouched here.
- ~~No Mongo behaviour battery~~ — **withdrawn, and the claim behind it was wrong.** See the
  section below.
- **`as_of` scans the chain in Python** rather than pushing the window down to the store. A chain
  is short by construction and the read is off stored columns, but a fact corrected thousands of
  times would feel it. §12 P3 already holds the query-option form.

## Mongo does keep the exemption — 2026-09-19

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-19T12:40:00Z
attempt: 2
claim: Mongo can enforce `skip_null` after all — a partialFilterExpression naming a field's stored BSON type excludes nulls, which `sparse` and `$exists: true` both fail to do
evidence: tests/integration/test_forze_mongo/test_mongo_document_versioned.py:138-186
action: decided
proposal: ASSUMED — the null exemption on Mongo is `{field: {$type: <stored type>}}`, derived from the field's annotation through the adapter's own storage mapping
```

The earlier position — recorded in RFC 0066's execution and repeated here — rested on a true
observation and a wrong conclusion. A `sparse` index *does* still index an explicit null, so it is
not the mechanism; it does not follow that no mechanism exists. A partial filter admits no
negation, but it admits `$type`, and naming what a field **is** excludes exactly the nulls the
exemption is about. For a compound tuple the conjunction indexes a document only when every field
is non-null, which is the same rule `skip_null` states.

Probed against a live server before any code was written:

| index | two explicit nulls | two rows sharing a real value |
|---|---|---|
| `sparse` | refused | refused |
| `$exists: true` | refused | refused |
| `$type` | **both accepted** | refused |

What this cost: the index spec carries the aggregate's read model, because the type comes from the
field's annotation through the adapter's own storage mapping — a UUID is written as a string here,
a Decimal as a Decimal128. A type that cannot be named is a refusal rather than a guess, and every
one of those refusal paths was uncovered until the coverage pass, which is where a `$type` value
given as a BSON type *number* was found to crash instead of refuse.

**What it changes:** correction lineage is no longer Postgres-shaped. A versioned aggregate runs on
Mongo, proved end to end against a real server.

**The lesson worth keeping:** "X does not work" is evidence about X, not about the space of
mechanisms. The earlier conclusion was stated in a capability declaration, a docstring, a docs page
and a changelog entry, and none of them was wrong about `sparse` — they were wrong about what
followed from it.

## Review — 2026-09-19

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-09-19T11:20:00Z
attempt: 1
claim: the generated UPDATE let a caller rewrite what a current version asserts in place — no successor, no correction record, and the earlier value gone — which is the thing the aggregate is declared to prevent
evidence: src/forze_kits/domain/versioned/mixins.py:65-78
action: decided
proposal: ASSUMED — a versioned row accepts no update that edits what it asserts; retiring it and soft-deleting it are the only writes that reach one, and `correct` is the path for everything else
```

D-1 says every write path must go through the kit's handlers and D-2 says a correction is never an
update in place, but neither settles what the aggregate's *own* generated `update` does. It did the
thing D-2 forbids. An earlier round closed the half that forged lineage — a patch carrying
`is_current` retired a fact through an ordinary update — by dropping those fields from the inbound
patch, and stopped there: the remaining half needed no lineage field at all, just a new value for
the fact.

The guard is on the update validator rather than on the operation, because the operation is not the
only way to the row — a repair script, a bulk update or a hand-written handler reaches it through
the port, which is what the superseded-row guard beside it already exists for. Soft deletion passes
because it hides a row without contradicting it, and the retiring write passes because it is how a
version becomes history at all.

evidence: src/forze_kits/domain/versioned/mixins.py:65-89

proposal: ASSUMED — the exemption is for the retirement *transition*: the row was current, the write leaves it not current, and `superseded_at` is stamped; a lineage field written any other way is refused

The first attempt read the diff's keys and asked whether they were the retiring write's keys.
They are the same keys in both directions. A transaction that retires the real head and reactivates
an older version leaves the fact with exactly one current version, so `single_current_head` is
satisfied and the chain now ends at a version something else already replaced — the successor is
still there, still pointing at the row that came back.

Half a retirement passes the same way: `is_current` cleared with `superseded_at` left null leaves a
version that was never in force and never replaced. The correction handler always writes both, so
requiring both costs the kit nothing and costs a direct writer the thing it was getting away with.
