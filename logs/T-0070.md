- Patch coverage over the touched unit and Postgres integration suites: 174 of 177 added

- `just test tests/integration/test_forze_postgres -n 4`: 1,080 passed, 1 failed. The
  failure is the isolation battery's fidelity matrix (`predicate_write_skew` at read
  committed), which touches no outbox code; it passed alone on rerun, so it reads as load
  timing under four workers.
- Mongo outbox and delivery conformance: 21 passed. The RabbitMQ and SQS suites that relay
  through `OutboxRelay`: 10 passed.

**Findings.**

1. *Prose (fixed, aa37be270).* `OutboxRelay`'s docstring said every row is claimed into
   `processing` and marked `published`, untrue under consume. The step's docstring said
   the backoff caps at `retry_max_backoff`; it never drops below `interval`.
2. *Docs gap (fixed, aa37be270).* §9 lists a retry policy on the query route as a
   documented risk; the schema page did not say it.
3. *Prose (fixed, b44bdb8eb).* A shutdown drain cut by its budget logged that its rows
   "may sit in 'processing' until reclaim", untrue when the pass rolls back.
4. *Test double (fixed, in the feature commit).* `test_drain_tick_isolates_a_failing_tenant`
   patched `_relay_once` to return `None`; it passed only because `and` short-circuited
   after the first tenant failed. Reading `stop` on it broke it. The double now returns a
   real `_RelayPass`.
5. *Open, by design.* Under consume, `mark_published` deletes by id without checking that
   it runs inside the pass that claimed the rows. A hand-driven relay that marks after its
   pass committed could delete a row another relay has since claimed, which that relay
   then publishes again. The RFC refuses only the claim outside a transaction; refusing the
   marks too would be a new decision.

**What I would still distrust.** The backoff integration test asserts timings with about
50 % slack on a 0.2 s base; it passed four runs in a row, but a heavily loaded runner
could stretch a tick. The idle-timeout test blocks the event loop for 1.5 s on purpose.

**Correction to self-audit finding 5 (2026-10-16).** It said a stale `mark_published`,
issued by a hand-driven relay after its own pass committed, "could delete a row another
relay has since claimed, which that relay then publishes again". The reviewer showed the
wording overstates it. The stale `DELETE` needs the row lock the other relay's pass holds,
so it waits for that pass. If the pass deleted the row, the stale `DELETE` finds nothing.
If the pass rolled back or rescheduled the row, the stale `DELETE` removes a row the stale
relay did publish. Either way the event was published, by one relay or both: the worst
case is a duplicate, never a lost row. The finding stays open as a duplicate risk only.
